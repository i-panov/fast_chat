# Fast Chat

Минималистичный мессенджер с федеративной архитектурой (как email). Go-бэкенд + React-фронтенд, real-time через SSE.

## Быстрый старт

```bash
make backend:run    # Go сервер на :8080
make frontend:run   # Vite dev-сервер на :5173
```

Открыть `http://localhost:5173`, зарегистрироваться по email с кодом подтверждения — готово.

## Стек

**Бэкенд:** Go 1.26, Huma v2 (HTTP-фреймворк поверх chi-адаптера), GORM + SQLite, SSE для реалтайма.

**Фронтенд:** React 19 + Mantine v9 + TanStack Router (file-based) + Tailwind v4 + react-i18next.

**Локализация.** Русский и английский. По умолчанию язык берётся из системы; переключается в меню аккаунта и на странице входа, выбор хранится в браузере. Новый язык добавляется JSON-файлом в `frontend/src/locales` и записью в `RESOURCES` в `frontend/src/i18n.ts`.

## Архитектура

### Структура бэкенда

Слои разделены: бизнес-логика не зависит от HTTP-фреймворка.

| Пакет | Ответственность |
|-------|-----------------|
| `transport` | Huma v2 API — все `/api/*` маршруты, auth/federation middleware, fallback к legacy mux |
| `service` | Бизнес-логика (auth, чаты, сообщения, файлы, федерация, sync, push) — без HTTP |
| `store` | Доступ к данным (GORM + SQLite), presence-счётчики |
| `federation` | RSA-подписи, `Manager` (verify/well-known) и `Client` (исходящие запросы с ретраями и фоновой очередью) |
| `sse` | Hub SSE-соединений, heartbeat, авторизация подключений |
| `push` | Web Push (RFC 8030), VAPID-ключи |
| `ratelimit` | In-memory rate limiter + извлечение клиентского IP |
| `internal/httputil` | Request ID, JSON-ответы |
| `internal/filestage` | Staging загрузок: MIME-сниффинг, хеширование, атомарный rename |
| `email`, `config`, `model`, `push` | Отправка писем, YAML-конфиг, модели данных |

Все `/api/*` домены обслуживает Huma; на legacy stdlib mux остались только health-пробы (`/healthz`, `/readyz`) и `/.well-known/fast-chat`, доступные через fallback-хендлер.

### Федерация (nick:domain)

Пользователь регистрируется как `alice:localhost:8080`. Сервер автоматически дописывает домен при регистрации.

**Поиск удалённого пользователя:** ввести `bob:other.com` в строку поиска — запрос уходит на свой сервер, тот проксирует на `other.com`.

**Создание чата / отправка:** клиент всегда общается со своим сервером. Сервер дублирует действия на удалённый сервер по HTTP (создание чата, отправка/редактирование/удаление сообщений).

**Федеративные эндпоинты** (`/api/federated/*`) — только сервер-сервер, с подписью RSA-SHA256; тело ограничено 1 МиБ. Запрос несёт заголовки:

| Заголовок | Значение |
|------------|----------|
| `X-Federation-Server` | Домен отправителя (он же идентичность в федерации) |
| `X-Federation-Timestamp` | Время запроса, окно 5 минут |
| `X-Federation-Nonce` | Случайное значение запроса: без него два одинаковых запроса в одну секунду получили бы одну подпись, и второй был бы отброшен как повтор |
| `X-Federation-Signature` | Подпись RSA-SHA256 над `server`, `method`, `uri`, `body`, `timestamp`, `nonce` (через `|`) |

Подпись покрывает nonce, поэтому его нельзя подменить после отправки, а
повтор запроса отбрасывается по паре «подпись + отправитель».

**Версии соседей.** Заголовок `X-Federation-Nonce` обязателен, поэтому
серверы разных версий не федерируются между собой: при rolling-апгрейде
федерация заработает только после обновления обеих сторон. Переговоров о
версии нет — это осознанное упрощение, цена которого — окно неработающей
федерации во время апгрейда.

**Доставка.** Исходящие операции не теряются: они складываются в очередь в базе и отправляются воркером с повторами (экспоненциальная задержка), пока сосед их не примет. Порядок операций одного соседа сохраняется: неудачная операция блокирует очередь соседа, иначе сообщение пришло бы раньше чата, к которому оно относится. Отказ, который повторится (4xx, кроме отказа по подписи, таймаута и лимита частоты), операцию снимает с громким логом — иначе она заблокировала бы соседа навсегда; сетевые ошибки, 5xx и отказ по подписи (расхождение часов или смена ключа соседа) ретраятся, но не бесконечно: после 50 попыток операция тоже снимается с громким логом. Обратная сторона — догоняющая синхронизация: сервер периодически забирает у соседей дельту (`GET /api/federated/sync`) и применяет её, поэтому сообщение, написанное во время недоступности соседа, всё равно доедет. Сосед также авторитетен по составу участников чата: изменение состава доезжает в catch-up.

**Шифрование между серверами.** E2EE-payload v3 пересылается как opaque
шифротекст: сервер-получатель не расшифровывает его. Публичный ключ, identity
и версия участника проксируются через
`GET /api/federated/users/{userId}/public-key`; TOFU-пиннинг identity работает
и для удалённых участников. Боты в федеративных чатах тоже используют v3.

**Чего федерация не умеет.** Смешанный деплой со старым протоколом: обе
стороны должны говорить protocol v2, иначе запросы получают явный 401/отказ.
Отдельного окна совместимости с v1 нет.

**Звонки.** Аудио/видео 1:1 между серверами поддержаны: владельцем звонка выступает сервер звонящего, сервер callee держит эфемерную тень и пересылает сигналинг. Подробности и ограничения — в разделе «Звонки».

### Чаты: приватные и групповые

Поддерживаются два типа:

- **Private** — чат между двумя пользователями, уникальный для пары (для той же пары всегда возвращается существующий).
- **Group** — чат с 3+ участниками, названием, владельцем (owner) и аватаркой. Групповые чаты с одинаковым составом **не уникальны** — можно создавать сколько угодно.

Группы создаются через `POST /api/chats` с payload `{type: "group", name, memberIds}`. **Создатель автоматически добавляется как owner** — указывать себя в `memberIds` не нужно. Минимальный состав — 1 (только owner); остальные добавляются позже через `POST /api/chats/{id}/members`. Все участники должны быть зарегистрированы на одном сервере (федеративные группы для MVP не поддерживаются). Владелец может переименовывать чат, добавлять/удалять участников, менять аватарку, удалять чат. Любой участник (кроме владельца) может выйти. Удаление/leave последнего участника запрещено — только `DELETE /api/chats/{id}` от владельца.

### Сессии

У аккаунта может быть несколько независимых сессий — по одной на устройство.
У каждого устройства свой токен, срок жизни и отзыв: вход на новом устройстве
не завершает остальные. Клиент присылает `deviceId` при входе; повторный вход
на том же устройстве обновляет его сессию, а не создаёт вторую.

- `POST /api/auth/logout` завершает только текущую сессию, `POST
  /api/auth/logout-all` — все сессии аккаунта.
- `GET /api/sessions` показывает устройства, `DELETE /api/sessions/{id}`
  отзывает выбранное. Отзыв немедленно закрывает SSE-поток и удаляет
  push-подписки этой сессии.
- Refresh меняет токен только своей сессии; другие устройства продолжают
  работать. Вкладки одного браузера сериализуют refresh через Web Locks и
  раздают новый токен через BroadcastChannel.
- В интерфейсе список устройств открывается из меню аккаунта («Устройства»); там же можно отозвать чужую сессию или выйти на всех устройствах.
- Аватар профиля загружается из меню аккаунта («Профиль»), хранится как обычный файл и виден в поиске и списке чатов.
- Реакции на сообщения — эмодзи с агрегатом по сообщению; изменения приходят по SSE и сохраняются локально.
- Голосовые сообщения записываются через `MediaRecorder` (до 5 минут), уходят как обычное вложение с шифрованием и проигрываются встроенным плеером с волной.
- Закреплённые сообщения хранятся отдельно от истории, показываются в шапке чата и синхронизируются через SSE.
- Блокировка пользователя скрывает его из поиска и запрещает новые личные чаты, сообщения и звонки; список блокировок доступен в меню аккаунта.
- Пересылка сообщения расшифровывает текст и вложения на клиенте и заново шифрует их для целевого чата.
- Поиск по сообщениям — клиентский, по локально загруженной и расшифрованной истории; сервер не получает поисковый индекс.
- Файловый кэш: до 200 записей и 200 МБ, LRU по последнему доступу; файлы крупнее 50 МБ не кэшируются автоматически, для видео есть «Сохранить офлайн».
- У группы нет искусственного лимита в 100 участников; ограничение снято, квоты при необходимости задаются отдельно.
- По умолчанию у аккаунта не больше 50 активных сессий
  (`auth.max_sessions_per_user`). `0` означает значение по умолчанию 50,
  отрицательное значение запрещено, безлимитного режима нет. При превышении
  лимита отзывается самая старая сессия; её SSE закрывается, а push-подписки
  удаляются.

При старте миграция `migrateLegacyUserColumns` переносит старый
`users.token` в `sessions` (пользователям без единой сессии) и удаляет
колонки `users.token`/`users.token_expires_at`. После миграции
аутентификация читает только `sessions`; повторный запуск миграции
безопасен.

### Реалтайм (SSE)

- Каждый клиент держит SSE-соединение со своим сервером.
- Сервер отправляет события: `new_message`, `message_updated`, `message_deleted`, `chat_created`, `chat_updated`, `chat_deleted`, `chat_member_added`, `chat_member_removed`, `thread_created`, `thread_message_new`, `thread_message_updated`, `typing`, `typing_stop`.
- Heartbeat каждые 30 секунд.

### Шифрование сообщений (E2E v3, мастер-ключ аккаунта)

Сообщения шифруются на клиенте: сервер хранит только шифротекст.

- **Один мастер-ключ на аккаунт**, а не на устройство или сессию: пара X25519
  для шифрования и пара Ed25519 (identity) для подписи. Приватные половины
  не покидают устройство в открытом виде.
- Один конверт на участника чата (`keyId` = id пользователя/бота). В конверте
  есть `keyVersion`; в профиле пользователя хранится текущая версия ключа.
  Ключ сообщения запечатывается `crypto_box_easy` для каждого участника.
- Текст, координаты, ключи вложений и их метаданные шифруются одним ключом
  сообщения (XChaCha20-Poly1305). AAD привязывает шифротекст к
  `chatId|messageId|fromId|threadId`; `createdAt` не входит, его назначает
  сервер после шифрования.
- Identity-подпись покрывает AAD и публичный ключ шифрования отправителя.
  Получатель пинит identity отправителя (TOFU) и принимает смену только по
  подписанной цепочке ротаций.
- Вложения шифруются отдельно, ключ файла едет внутри зашифрованного
  сообщения. Сервер видит только шифротекст, SHA-256 исходного содержимого
  (для дедупликации) и факт шифрования.
- Резервная копия (v4) содержит обе пары, версию и историю ключей/identity.
  Она завёрнута паролем (PBKDF2-SHA256, 310k итераций) и, опционально,
  WebAuthn PRF passkey. Сервер не может открыть ни одну обёртку.

**Несколько устройств.** Все устройства используют один мастер-ключ и
восстанавливают его из серверного бэкапа по паролю или passkey. После
создания первого ключа приложение требует сохранить бэкап. Если ключа нет,
а бэкап есть, показывается восстановление; молча новый ключ не генерируется.

**Ротация.** Ключ шифрования и ключ подписи меняются вручную и независимо.
Ротация увеличивает `masterKeyVersion`, сохраняет старую пару в истории и
пишет новый бэкап; signing-ротация добавляет подписанное звено identity-цепочки.
Ротация запрещена при включённом PIN/passkey и при passkey-обёртке серверного
бэкапа, чтобы новый ключ не остался без источника восстановления.

**Локальная защита.** PIN на 6 цифр и/или passkey (WebAuthn PRF) шифруют
мастер-ключ и историю в IndexedDB. Автоблокировка настраивается отдельно:
бездействие, уход в фон, заморозка/закрытие, сон/блокировка экрана. При
закрытом локе расшифрованные сообщения и вложения не остаются в памяти/DOM.

**Совместимость.** Сервер принимает только payload `v = 3`; v1/v2
отклоняются. Формат ключей и сообщений несовместим с прежней БД: серверную
БД и IndexedDB клиентов нужно удалить при переходе. Старые клиенты и
федеративные пиры без protocol v2 не поддерживаются.

Что сервер всё равно видит: участников чата, время, размеры и количество
сообщений, факт шифрования и хеш шифротекста/плейнтекста для дедупликации.
Публичные ключи раздаёт сервер, поэтому подмена ключа/identity на сервере
остаётся в модели угроз; цепочка identity и TOFU-пины позволяют заметить
смену, но не защищают от сервера, который выдаёт себя за пользователя с
самого начала.

## Наблюдаемость

### Заголовки безопасности

Ответы содержат `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
`Referrer-Policy: strict-origin-when-cross-origin` и
`Content-Security-Policy` (скрипты и стили только свои, карты — с
`*.tile.openstreetmap.org`). `blob:` разрешён в `img-src`, `media-src` и
`connect-src`: вложения расшифровываются в объектные URL локально, и без него
зашифрованные картинки, видео и аудио не отображались на боевой сборке.

`Strict-Transport-Security` добавляется, когда соединение защищено: напрямую
по TLS или через доверенный обратный прокси, который сообщает схему в
`X-Forwarded-Proto`. Заголовок доверия берётся только у прокси из
`server.trusted_proxies` — иначе клиент мог бы объявить себя защищённым.

### Health probes

- `GET /healthz` — liveness probe (всегда 200, процесс жив).
- `GET /readyz` — readiness probe (проверяет DB, 503 если недоступна).

Используются оркестраторами (k8s, Docker) для проверки состояния.

### Request logging

Каждый HTTP-запрос логируется через `slog` с полями: `method`, `path`, `status`, `duration`, `remote_addr`, `request_id`. Уровень `Info` для успешных (<400), `Warn` для ошибок.

### Request ID

Сервер принимает/генерирует `X-Request-ID` и:
- возвращает его в response headers;
- пробрасывает во все логи запроса;
- передаёт в федеративные запросы для сквозной трассировки между серверами.

## Тестирование федерации

Два инстанса:

```bash
# Терминал 1 (alice@localhost:8080)
make backend:run
make frontend:run

# Терминал 2 (bob@localhost:8081)
make backend:run BACKEND_PORT=8081 FRONTEND_PORT=5174
make frontend:run FRONTEND_PORT=5174 API_PROXY=http://localhost:8081
```

Порт инстанса определяет его базу (`/tmp/fastchat-<порт>.db`) и каталог
загрузок, поэтому второй сервер не мешает первому. Домен сервера (часть
идентичности `nick:domain` в федерации) по умолчанию вычисляется из
`server.host` и `server.port` — для локального инстанса этого достаточно.
Если `server.host` — адрес бинда, недоступный снаружи (`127.0.0.1` за
реверс-прокси, `0.0.0.0`), задайте `server.public_domain`.
Дев-сервер по умолчанию слушает `localhost` и поэтому недоступен из локальной
сети; для проверки с телефона задайте `FASTCHAT_HOST=0.0.0.0` и
`FASTCHAT_PUBLIC_DOMAIN=192.168.x.y:<порт>`.

**Смена `public_domain` меняет идентичность.** Идентификатор пользователя
содержит домен (`nick:domain`) и перерегистрировать его нельзя, поэтому при
смене домена существующую базу нужно пересоздать или отдельно мигрировать
идентификаторы.

1. Зарегистрировать `alice` на `:5173`, `bob` на `:5174`.
2. На `:5173` найти `bob:localhost:8081`.
3. Создать чат — сообщения синхронизируются между серверами.

Федеративные звонки проверяются автоматически:

```bash
make frontend:e2e:federated
```

Playwright сам поднимает два бэкенда (`:8082` и `:8083`) и два dev-сервера
(`:5175` и `:5176`) с отдельными БД, загрузками и каталогами ключей. Сценарии:
медиа A→B и B→A, decline, reload звонящего (`peer-left`), audio-only и hangup
callee. Обычный `make frontend:e2e` использует другие порты, поэтому оба
набора можно запускать на одной машине.

## PWA / Offline-first

Приложение работает как PWA: Service Worker (injectManifest) с workbox кэширует API-запросы (NetworkFirst) и файлы (CacheFirst). В production-сборке SW регистрируется автоматически; в dev-режиме отключён (`devOptions.enabled: false`).

**Offline-first:**
- Сообщения, файлы и треды сохраняются в IndexedDB (одна база на аккаунт).
- Отправка через outbox: при офлайне сообщение ставится в очередь и отправляется при восстановлении соединения.
- Можно отменить отправку (cancel-send) для сообщений в очереди.
- Авто-повтор неудачных отправок при реконнекте.

**Дельта синхронизации** (`GET /api/sync?since=`):
- список чатов приходит целиком, а не дельтой: чат, в который добавили
  участника или переименовали, не меняет дату создания, и «изменённые с
  момента X» такие чаты бы потеряло;
- сообщения приходят только изменённые с момента `since`; сообщения тредов
  идут отдельным списком (`threadMessages`), потому что клиент держит их в
  отдельном хранилище;
- удаления приходят отдельными tombstone'ами — по ним клиент убирает чат
  (например, если его исключили из группы, пока он был офлайн) и помечает
  сообщения удалёнными.

**Вложения.** Файл принадлежит загрузившему его аккаунту: прикрепить его к
сообщению может только владелец. Поэтому id или хеш файла, утекшие из чата,
не дают бывшему участнику вернуть себе доступ к содержимому после выхода из
группы.

## WebPush

Push-уведомления для офлайн-устройств. VAPID-ключи генерируются автоматически при первом запуске (хранятся в `push.key_path`, по умолчанию `./keys`).

**Сценарий:**
1. Пользователь логинится → браузер запрашивает разрешение на уведомления.
2. Браузер подписывается → endpoint сохраняется на сервере (`POST /api/push/subscribe`) вместе с текущей сессией.
3. При отправке сообщения сервер проверяет, какие сессии получателя онлайн.
4. Офлайн-сессиям отправляет push через их браузерный push-сервис: если телефон онлайн, а ноутбук нет, телефон получит событие по SSE, а ноутбук — push.
5. При клике на уведомление открывается чат (или фокусируется существующее окно).

**Триггеры:** `new_message` и `thread_message_new`. Push отправляется только не-отправителю и только офлайн-сессиям получателя; онлайн-устройства получают событие по SSE. Входящий звонок уходит по SSE всем онлайн-сессиям, а офлайн-сессиям — push.

## Звонки

Звонок идёт между двумя пользователями приватного чата — на одном сервере
или на разных (федерация). Медиа передаётся напрямую между браузерами
(P2P, DTLS-SRTP), сервер только согласует соединение и передаёт служебные
сообщения.

- Кнопка звонка — в шапке приватного чата, в том числе для собеседника с
  другого сервера. Групповых звонков и звонков в «Избранном» нет.
- Сигнализация идёт по существующему транспорту: SSE приносит входящие
  события (`call_incoming`, `call_accepted`, `call_ended`, `call_ice`), REST
  принимает действия (`POST /api/calls`, `.../accept`, `.../reject`,
  `.../hangup`, `.../ice`, `GET /api/calls/current`).
- Федеративный звонок ведёт сервер звонящего (владелец); сервер callee
  держит эфемерную тень и пересылает сигналинг владельцу. Серверы
  обмениваются подписанными запросами `/api/federated/calls/*`.
- ICE-конфиги сторон передаются в `invite/accept`, и клиент собирает
  union STUN/TURN обоих серверов. Ограничение MVP: caller создаёт соединение
  до получения конфига callee, поэтому union применяется только у callee.
- Медиа шифрует сам WebRTC (DTLS-SRTP): сервер видит SDP и кандидатов, но не
  байты медиа.
- Входящий звонок приходит по SSE всем онлайн-сессиям; офлайн-сессиям — push-уведомление.
- Собеседник ждёт ответа 45 секунд. Страница, которая уходит (закрыли
  вкладку, перезагрузили), отдаёт `peer-left`, чтобы вторая сторона не ждала
  таймаута.
- Звонок один на аккаунт: второму вызову сервер отвечает отказом с кодом
  `busy-caller` или `busy-callee`.
- Без камеры звонок продолжается только со звуком: превью и кнопка камеры
  в этом режиме скрыты.

**Сеть.** Прямое соединение не проходит в части сетей (symmetric NAT,
мобильные операторы, корпоративные firewall'ы): для них нужен TURN-релей.
Он поднимается отдельно; готовый Docker-деплой лежит в `deploy/coturn/` (см. `deploy/coturn/README.md`).

```yaml
ice:
    stun:
        - "stun:stun.l.google.com:19302"
    turn:
        # TURN REST API: в coturn это use-auth-secret и тот же
        # static-auth-secret. Сервер выдаёт каждому авторизованному клиенту
        # короткоживущие (1 час) учётные данные: имя "<expiry>:<userID>",
        # пароль — HMAC-SHA1 от имени.
        - urls:
              - "turn:turn.example.com:3478?transport=udp"
              - "turn:turn.example.com:3478?transport=tcp"
          secret: "<TURN_STATIC_AUTH_SECRET>"
```

Статический вариант с `username` и `credential` тоже поддерживается, но при
старте сервер предупреждает: такой пароль получает любой, кто открыл сайт, и
релей остаётся открытым для всех. `GET /api/ice` отдаёт конфигурацию только
авторизованным, поэтому в публичном `/api/config` её нет.

**Требования.** `getUserMedia` работает только по HTTPS (кроме
`localhost`), поэтому интерфейс нужно публиковать по TLS.

**Чего нет.** Групповых звонков, записи.

### Федеративные группы (базовая репликация)

Группа создаётся на сервере владельца и может включать пользователей других
серверов. Владелец рассылает реплику через `POST /api/federated/groups`;
серверы участников хранят копию с `RemoteServer = домен владельца`.
Сообщения владельца уходят на каждый сервер-участник, а сообщения удалённого
участника владелец пересылает остальным серверам. Вложения передаются как
метаданные, а байты забираются через подписанный
`GET /api/federated/files/{fileId}` с сервера-источника (`/api/files/{id}`
проксирует запрос). Добавление/удаление участников, переименование и удаление
группы реплицируются на серверы участников подписанными запросами.
