# Fast Chat

Минималистичный мессенджер с федеративной архитектурой (как email). Go-бэкенд + React-фронтенд, real-time через SSE.

## Быстрый старт

```bash
make backend:run    # Go сервер на :8080
make frontend:run   # Vite dev-сервер на :5173
```

Открыть `http://localhost:5173`, зарегистрироваться по email с кодом подтверждения — готово.

## Стек

**Бэкенд:** Go 1.26, Huma v2 (HTTP-фреймворк поверх chi-адаптера), GORM + SQLite, SSE для реалтайма.

**Фронтенд:** React 19 + Mantine v9 + TanStack Router (file-based) + Tailwind v4 + react-i18next.

## Архитектура

### Структура бэкенда

Слои разделены: бизнес-логика не зависит от HTTP-фреймворка.

| Пакет | Ответственность |
|-------|-----------------|
| `transport` | Huma v2 API — все `/api/*` маршруты, auth/federation middleware, fallback к legacy mux |
| `service` | Бизнес-логика (auth, чаты, сообщения, файлы, федерация, sync, push) — без HTTP |
| `store` | Доступ к данным (GORM + SQLite), presence-счётчики |
| `federation` | RSA-подписи, `Manager` (verify/well-known) и `Client` (исходящие запросы с ретраями и фоновой очередью) |
| `sse` | Hub SSE-соединений, heartbeat, авторизация подключений |
| `push` | Web Push (RFC 8030), VAPID-ключи |
| `ratelimit` | In-memory rate limiter + извлечение клиентского IP |
| `internal/httputil` | Request ID, JSON-ответы |
| `internal/filestage` | Staging загрузок: MIME-сниффинг, хеширование, атомарный rename |
| `email`, `config`, `model`, `push` | Отправка писем, YAML-конфиг, модели данных |

Все `/api/*` домены обслуживает Huma; на legacy stdlib mux остались только health-пробы (`/healthz`, `/readyz`) и `/.well-known/fast-chat`, доступные через fallback-хендлер.

### Федерация (nick:domain)

Пользователь регистрируется как `alice:localhost:8080`. Сервер автоматически дописывает домен при регистрации.

**Поиск удалённого пользователя:** ввести `bob:other.com` в строку поиска — запрос уходит на свой сервер, тот проксирует на `other.com`.

**Создание чата / отправка:** клиент всегда общается со своим сервером. Сервер дублирует действия на удалённый сервер по HTTP (создание чата, отправка/редактирование/удаление сообщений).

**Федеративные эндпоинты** (`/api/federated/*`) — только сервер-сервер, с подписью RSA-SHA256; тело ограничено 1 МиБ. Запрос несёт заголовки:

| Заголовок | Значение |
|------------|----------|
| `X-Federation-Server` | Домен отправителя (он же идентичность в федерации) |
| `X-Federation-Timestamp` | Время запроса, окно 5 минут |
| `X-Federation-Nonce` | Случайное значение запроса: без него два одинаковых запроса в одну секунду получили бы одну подпись, и второй был бы отброшен как повтор |
| `X-Federation-Signature` | Подпись RSA-SHA256 над `server`, `method`, `uri`, `body`, `timestamp`, `nonce` (через `|`) |

Подпись покрывает nonce, поэтому его нельзя подменить после отправки, а
повтор запроса отбрасывается по паре «подпись + отправитель».

**Версии соседей.** Заголовок `X-Federation-Nonce` обязателен, поэтому
серверы разных версий не федерируются между собой: при rolling-апгрейде
федерация заработает только после обновления обеих сторон. Переговоров о
версии нет — это осознанное упрощение, цена которого — окно неработающей
федерации во время апгрейда.

**Доставка.** Исходящие операции не теряются: они складываются в очередь в базе и отправляются воркером с повторами (экспоненциальная задержка), пока сосед их не примет. Порядок операций одного соседа сохраняется: неудачная операция блокирует очередь соседа, иначе сообщение пришло бы раньше чата, к которому оно относится. Отказ, который повторится (4xx, кроме отказа по подписи, таймаута и лимита частоты), операцию снимает с громким логом — иначе она заблокировала бы соседа навсегда; сетевые ошибки, 5xx и отказ по подписи (расхождение часов или смена ключа соседа) ретраятся, но не бесконечно: после 50 попыток операция тоже снимается с громким логом. Обратная сторона — догоняющая синхронизация: сервер периодически забирает у соседей дельту (`GET /api/federated/sync`) и применяет её, поэтому сообщение, написанное во время недоступности соседа, всё равно доедет. Сосед также авторитетен по составу участников чата: изменение состава доезжает в catch-up.

**Чего федерация не умеет.** Вложения не передаются: у соседа нет файла, и endpoint'а, который бы его отдал, пока нет. Сообщение с картинкой дойдёт до соседа без картинки. Передача вложений — отдельная задача: ей нужны endpoint, политика размера и перенос зашифрованного содержимого.

### Чаты: приватные и групповые

Поддерживаются два типа:

- **Private** — чат между двумя пользователями, уникальный для пары (для той же пары всегда возвращается существующий).
- **Group** — чат с 3+ участниками, названием, владельцем (owner) и аватаркой. Групповые чаты с одинаковым составом **не уникальны** — можно создавать сколько угодно.

Группы создаются через `POST /api/chats` с payload `{type: "group", name, memberIds}`. **Создатель автоматически добавляется как owner** — указывать себя в `memberIds` не нужно. Минимальный состав — 1 (только owner); остальные добавляются позже через `POST /api/chats/{id}/members`. Все участники должны быть зарегистрированы на одном сервере (федеративные группы для MVP не поддерживаются). Владелец может переименовывать чат, добавлять/удалять участников, менять аватарку, удалять чат. Любой участник (кроме владельца) может выйти. Удаление/leave последнего участника запрещено — только `DELETE /api/chats/{id}` от владельца.

### Сессии

Токен принадлежит аккаунту, а не устройству: у аккаунта одна сессия. Вход
с другого устройства завершает предыдущую, и выход отзывает токен аккаунта на
всех устройствах. Сессии по устройствам потребовали бы отдельной таблицы и
миграции схемы — это отдельная задача.

### Реалтайм (SSE)

- Каждый клиент держит SSE-соединение со своим сервером.
- Сервер отправляет события: `new_message`, `message_updated`, `message_deleted`, `chat_created`, `chat_updated`, `chat_deleted`, `chat_member_added`, `chat_member_removed`, `thread_created`, `thread_message_new`, `thread_message_updated`, `typing`, `typing_stop`.
- Heartbeat каждые 30 секунд.

### Шифрование сообщений (E2E)

Сообщения шифруются на клиенте: сервер хранит только шифротекст.

- На аккаунте генерируется пара ключей X25519 (`crypto_box_seal`); приватный
  ключ не покидает устройство, публичный загружается на сервер.
- Текст, координаты, ключи вложений и их метаданные шифруются одним ключом
  сообщения (XChaCha20-Poly1305), а сам ключ запечатывается публичным ключом
  каждого участника чата.
- Вложения шифруются отдельно, ключ файла едет внутри зашифрованного
  сообщения.
- Резервная копия приватного ключа шифруется паролем (PBKDF2-SHA256, 310k
  итераций) и хранится на сервере как непрозрачный блоб: без пароля ключ не
  восстановить.

Что сервер всё равно видит: участников чата, время, размеры и количество
сообщений, а для зашифрованных вложений — SHA-256 исходного содержимого
(нужен для дедупликации) и то, что файл зашифрован. Ключи участников
раздаёт сервер, поэтому доверять ему приходится: подмена публичного ключа
позволит читать сообщения.

## Наблюдаемость

### Заголовки безопасности

Ответы содержат `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
`Referrer-Policy: strict-origin-when-cross-origin` и
`Content-Security-Policy` (скрипты и стили только свои, карты — с
`*.tile.openstreetmap.org`).

`Strict-Transport-Security` добавляется, когда соединение защищено: напрямую
по TLS или через доверенный обратный прокси, который сообщает схему в
`X-Forwarded-Proto`. Заголовок доверия берётся только у прокси из
`server.trusted_proxies` — иначе клиент мог бы объявить себя защищённым.

### Health probes

- `GET /healthz` — liveness probe (всегда 200, процесс жив).
- `GET /readyz` — readiness probe (проверяет DB, 503 если недоступна).

Используются оркестраторами (k8s, Docker) для проверки состояния.

### Request logging

Каждый HTTP-запрос логируется через `slog` с полями: `method`, `path`, `status`, `duration`, `remote_addr`, `request_id`. Уровень `Info` для успешных (<400), `Warn` для ошибок.

### Request ID

Сервер принимает/генерирует `X-Request-ID` и:
- возвращает его в response headers;
- пробрасывает во все логи запроса;
- передаёт в федеративные запросы для сквозной трассировки между серверами.

## Тестирование федерации

Два инстанса:

```bash
# Терминал 1 (alice@localhost:8080)
make backend:run
make frontend:run

# Терминал 2 (bob@localhost:8081)
make backend:run BACKEND_PORT=8081 FRONTEND_PORT=5174
make frontend:run FRONTEND_PORT=5174 API_PROXY=http://localhost:8081
```

Порт инстанса определяет его базу (`/tmp/fastchat-<порт>.db`) и каталог
загрузок, поэтому второй сервер не мешает первому. Домен сервера вычисляется
из `server.host` и `server.port` — они и есть идентичность в федерации.

1. Зарегистрировать `alice` на `:5173`, `bob` на `:5174`.
2. На `:5173` найти `bob:localhost:8081`.
3. Создать чат — сообщения синхронизируются между серверами.

## PWA / Offline-first

Приложение работает как PWA: Service Worker (injectManifest) с workbox кэширует API-запросы (NetworkFirst) и файлы (CacheFirst). В production-сборке SW регистрируется автоматически; в dev-режиме отключён (`devOptions.enabled: false`).

**Offline-first:**
- Сообщения, файлы и треды сохраняются в IndexedDB (одна база на аккаунт).
- Отправка через outbox: при офлайне сообщение ставится в очередь и отправляется при восстановлении соединения.
- Можно отменить отправку (cancel-send) для сообщений в очереди.
- Авто-повтор неудачных отправок при реконнекте.

**Дельта синхронизации** (`GET /api/sync?since=`):
- список чатов приходит целиком, а не дельтой: чат, в который добавили
  участника или переименовали, не меняет дату создания, и «изменённые с
  момента X» такие чаты бы потеряло;
- сообщения приходят только изменённые с момента `since`; сообщения тредов
  идут отдельным списком (`threadMessages`), потому что клиент держит их в
  отдельном хранилище;
- удаления приходят отдельными tombstone'ами — по ним клиент убирает чат
  (например, если его исключили из группы, пока он был офлайн) и помечает
  сообщения удалёнными.

**Вложения.** Файл принадлежит загрузившему его аккаунту: прикрепить его к
сообщению может только владелец. Поэтому id или хеш файла, утекшие из чата,
не дают бывшему участнику вернуть себе доступ к содержимому после выхода из
группы.

## WebPush

Push-уведомления для офлайн-пользователей. VAPID-ключи генерируются автоматически при первом запуске (хранятся в `push.key_path`, по умолчанию `./keys`).

**Сценарий:**
1. Пользователь логинится → браузер запрашивает разрешение на уведомления.
2. Браузер подписывается → endpoint сохраняется на сервере (`POST /api/push/subscribe`).
3. При отправке сообщения сервер проверяет, онлайн ли получатель.
4. Если получатель офлайн — отправляет push через его браузерный push-сервис.
5. При клике на уведомление открывается чат (или фокусируется существующее окно).

**Триггеры:** `new_message` и `thread_message_new`. Push отправляется только не-отправителю, только если получатель офлайн.

## Звонки

Звонок идёт между двумя пользователями одного приватного чата на одном
сервере: медиа передаётся напрямую между браузерами (P2P), сервер только
согласует соединение и передаёт служебные сообщения.

- Кнопка звонка — в шапке приватного чата. У собеседника с другого сервера
  кнопки нет: федеративные и групповые звонки не поддержаны, в «Избранном»
  звонка тоже нет.
- Сигнализация идёт по существующему транспорту: SSE приносит входящие
  события (`call_incoming`, `call_accepted`, `call_ended`, `call_ice`), REST
  принимает действия (`POST /api/calls`, `.../accept`, `.../reject`,
  `.../hangup`, `.../ice`, `GET /api/calls/current`).
- Медиа шифрует сам WebRTC (DTLS-SRTP): сервер видит SDP и кандидатов, но не
  байты медиа.
- Входящий звонок приходит по SSE; офлайн-получателю — push-уведомление.
- Собеседник ждёт ответа 45 секунд. Страница, которая уходит (закрыли
  вкладку, перезагрузили), отдаёт `peer-left`, чтобы вторая сторона не ждала
  таймаута.
- Звонок один на аккаунт: второму вызову сервер отвечает отказом с кодом
  `busy-caller` или `busy-callee`.

**Сеть.** Прямое соединение не проходит в части сетей (symmetric NAT,
мобильные операторы, корпоративные firewall'ы): для них нужен TURN-релей.
Он поднимается отдельно (coturn) и в репозиторий не входит.

```yaml
ice:
    stun:
        - "stun:stun.l.google.com:19302"
    turn:
        # TURN REST API: в coturn это use-auth-secret и тот же
        # static-auth-secret. Сервер выдаёт каждому авторизованному клиенту
        # короткоживущие (1 час) учётные данные: имя "<expiry>:<userID>",
        # пароль — HMAC-SHA1 от имени.
        - urls:
              - "turn:turn.example.com:3478?transport=udp"
              - "turn:turn.example.com:3478?transport=tcp"
          secret: "<TURN_STATIC_AUTH_SECRET>"
```

Статический вариант с `username` и `credential` тоже поддерживается, но при
старте сервер предупреждает: такой пароль получает любой, кто открыл сайт, и
релей остаётся открытым для всех. `GET /api/ice` отдаёт конфигурацию только
авторизованным, поэтому в публичном `/api/config` её нет.

**Требования.** `getUserMedia` работает только по HTTPS (кроме
`localhost`), поэтому интерфейс нужно публиковать по TLS.

**Чего нет.** Групповых звонков, федеративных звонков, записи.

## Конфигурация

Бэкенд читает YAML-конфигурацию из файла, переданного через `--config`.

Пример для production: `config/prod.yaml.example` (скопировать в `config/prod.yaml` и заполнить).

### Основные параметры

| Параметр YAML | По умолчанию | Описание |
|---------------|--------------|----------|
| `server.host` | `localhost` | Адрес для бинда |
| `server.port` | `8080` | Порт сервера |
| `server.static_dir` | `../frontend/dist` | Путь к собранному фронтенду |
| `database.path` | — (required) | Путь к SQLite файлу |
| `cors.origin` | — | Разрешённый origin для CORS |
| `federation.scheme` | `https` | Протокол для федерации (`http`/`https`) |
| `federation.allow_private_addresses` | `false` | Разрешить соседей на приватных адресах (только для локальной разработки) |
| `federation.timeout` | `10` | Таймаут федеративных запросов (сек) |
| `auth.token_expiry` | `24h` | Время жизни токена сессии |
| `auth.token_expiry_warning` | `5m` | Когда предупреждать об истечении |
| `email.debug_mode` | `true` | `true` = писать письма в логи, `false` = отправлять через SMTP |
| `push.vapid_subject` | — | VAPID subject (обычно `mailto:`) |

Значения файла перекрываются переменными окружения — так второй локальный
инстанс запускается из того же конфига:

| Переменная | Описание |
|------------|----------|
| `FASTCHAT_HOST` | Заменяет `server.host` (домен сервера вычисляется из хоста и порта) |
| `FASTCHAT_PORT` | Заменяет `server.port` |
| `FASTCHAT_DB_PATH` | Заменяет `database.path` |
| `FASTCHAT_UPLOADS_DIR` | Заменяет `uploads.dir` |
| `FASTCHAT_CORS_ORIGIN` | Заменяет `cors.origin` |
| `FASTCHAT_FEDERATION_SCHEME` | Заменяет `federation.scheme` |

Переменные окружения для фронта (dev):

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `VITE_API_PROXY` | `http://localhost:8080` | Адрес бэкенда для Vite proxy |

make build              # Собрать бэкенд + фронтенд
