# Звонки 1:1 через WebRTC — дизайн

Дата: 2026-10-20
Статус: согласован, готов к планированию реализации

## 1. Контекст и цель

В проекте уже есть работающий real-time: SSE-хаб для событий, WebPush для
офлайн-уведомлений, E2E-шифрование сообщений, федерация между серверами.
Пользователи просят звонки.

Цель первого инкремента — **аудио- и видеозвонок между двумя пользователями
одного приватного чата, живущими на одном сервере**.

Медиа идёт напрямую между браузерами (P2P). Сервер проекта не участвует в
передаче медиа: он только согласует соединение (сигналинг) и хранит
состояние звонка. Coturn поднимается отдельно и используется как запасной
путь, когда прямое соединение невозможно.

## 2. Границы MVP

Входит:

- звонок 1:1 из приватного чата (не self-чат, не группа);
- аудио и видео сразу, одним `getUserMedia`;
- модель «звонящий / принимающий»: принять, отклонить, отменить, «занято»,
  таймаут неответа;
- сигналинг через существующий SSE и REST;
- TURN через coturn как запасной путь;
- уведомление о входящем звонке через WebPush, если получатель офлайн;
- e2e-тесты на Playwright с двумя браузерами.

Не входит (осознанно):

- групповые звонки и любой медиасервер (SFU);
- федеративные звонки (звонок между разными серверами);
- запись звонков;
- звонки в self-чате и группах;
- переподключение P2P-соединения после перезагрузки страницы.

Федеративные звонки и SFU — отдельные задачи после того, как P2P-звонок
устоится.

## 3. Обзор архитектуры

```
звонящий A                    сервер                     принимающий B
     |                            |                             |
     |-- getUserMedia, PC -------->|                             |
     |-- createOffer              |                             |
     |-- POST /api/calls -------->|                             |
     |   {chatId, offer}          |-- проверки, звонок=ringing  |
     |                            |-- call_incoming + offer --->|
     |                            |     (или WebPush, если B офлайн)
     |-- POST .../ice (кандидаты)->|-- call_ice ---------------->|
     |                            |                             |
     |                            |<-- POST .../accept {answer}-|
     |                            |-- call_accepted + answer -->|
     |-- setRemoteDescription     |                             |
     |========== медиа P2P (DTLS-SRTP) =========================|
     |                            |                             |
     |-- POST .../hangup -------->|-- call_ended ------------->|
```

Медиа шифруется самим WebRTC (DTLS-SRTP) между участниками. Сервер, если он
не TURN-узел, байтов медиа не видит — отдельный слой E2E-шифрования не
нужен.

## 4. Серверная часть

### 4.1 Пакет `backend/calls`

Реестр звонков в памяти процесса — инфраструктура рядом с `sse` и `push`,
без обращений к БД. От `store` пакет не зависит: идентификаторы звонков
генерируются новым нейтральным пакетом `internal/ids`, который использует и
`store` (существующий `store.GenerateID` остаётся обёрткой над ним, чтобы не
трогать его вызовы).

```go
type State string

const (
    StateRinging  State = "ringing"
    StateActive   State = "active"
    StateEnded    State = "ended"
)

type Call struct {
    ID        string
    CallerID  string
    CalleeID  string
    ChatID    string
    State     State
    Offer     string   // SDP вызывающего, нужен офлайн-принимающему
    Answer    string   // SDP принявшего
    CreatedAt time.Time
    ExpiresAt time.Time  // CreatedAt + окно ringing
    EndedAt   time.Time
    Reason    string
}

type Manager struct { ... }
```

Менеджер отвечает за:

- карту звонков и два индекса: «пользователь → активный звонок» и
  «пользователь → последний завершённый звонок» (срок жизни 10 минут).
  Второй индекс нужен `GET /api/calls/current`: завершённый звонок в
  первом не лежит, и обход карты звонков на каждый запрос — лишняя работа;
- переходы состояний;
- таймеры: `ringing` → 45 секунд → `ended{reason: timeout}`; `active` → TTL
  4 часа. Уборщик снимает зависший активный звонок, когда собеседник офлайн
  дольше минуты; если таймер по какой-то причине не сработал, звонок
  всё равно снимается жёстким TTL — иначе он держал бы индекс
  «пользователь → активный звонок», и пользователь до четырёх часов
  получал бы `409` на любой звонок;
- источник присутствия для уборщика — колбэк `OfflineSince func(userID
  string) time.Time`, который внедряется в менеджер снаружи (сервис
  подключает его к `store.OfflineSince` — тому же источнику присутствия,
  что и `store.IsOnline`; он читает карту в памяти, а не ходит в БД).
  Нужен не флаг, а время: короткий обрыв сети — это не уход из звонка.
  Нулевое время означает «онлайн» (или пользователь ещё не подключался).
  Пакет от `store` не зависит: колбэк — это параметр, а не импорт;
- **колбэк не вызывается под мьютексом менеджера и не из обработчиков
  запросов.** Уборщик снимает кандидатов и проверяет их присутствие вне
  блокировки, затем берёт мьютекс и применяет решение. Иначе проверка
  присутствия задерживала бы создание и принятие звонков на всё время
  проверки — а под блокировкой менеджера она держала бы и создание, и
  принятие;
- **минута простоя — граница между обрывом сети и уходом клиента.** Медиа
  P2P от сервера не зависит, поэтому короткий обрыв SSE звонок не рвёт:
  клиент переподключается, а присутствие возвращается вместе с ним. Клиент,
  который не вернулся (падение браузера, закрытая вкладка), освобождает
  звонок в пределах минуты плюс тик уборщика, а не через четыре часа;
- уборку завершённых звонков: запись живёт ещё 10 минут после `ended`
  (за это время клиент забирает финальное состояние и видит «пропущенный
  звонок»), потом удаляется. При переходе в `ended` SDP очищается, чтобы
  память не держала SDP завершённых звонков;
- `Close()` при остановке сервера (закрывает все звонки, чтобы клиенты
  получили `call_ended`). Вызывается **строго до** `sse.Hub.Close()`: после
  закрытия хаба события уже никому не уйдут.

**Почему offer и answer хранятся в реестре, а не пересылаются «на лету»:**
если собеседник офлайн, событие `call_incoming` теряется. Получив push и
открыв приложение, он должен получить offer — иначе принять звонок нечем.
Поэтому SDP лежит в звонке, пока звонок `ringing` (окно 45 секунд), а не
«до конца звонка»: после таймаута звонок уже никто не примет, и SDP в нём
больше не нужен.

### 4.2 `service/calls.go`

Бизнес-правила, без HTTP:

- кому можно звонить: пользователь — участник приватного чата 1:1, чат не
  self, собеседник — другой участник;
- **собеседник должен быть локальным**. `service.RemoteServerFromID(id)`
  возвращает домен и для локального пользователя (идентификатор у всех вида
  `nick:домен`), поэтому федеративность определяется сравнением с
  `cfg.Server.Domain` — как в `AddChatMember`
  (`backend/service/chat.go:308-311`): домен непустой и не равен нашему →
  звонок отклоняется с `403` («звонки между серверами не поддержаны»).
  Иначе `call_incoming` ушёл бы на идентификатор, которого на этом сервере
  нет, и вызывающий ждал бы впустую;
- проверка занятости: у пользователя один активный звонок. Звонок занятому
  собеседнику и звонок от пользователя, который сам уже в звонке, →
  `ErrCallBusy` (`409`), но с разными сообщениями;
- переходы состояний и права на `accept` / `reject` / `hangup` / `ice`:
  принимать и отклонять может только звонящий и принимающий соответственно;
- **причину завершения назначает сервер**. Из тела `hangup` принимается
  только `peer-left` — уточнение от клиента, который перезагрузил страницу;
  пустое тело даёт `hangup`; любое другое значение отбрасывается и
  подставляется `hangup`. Иначе клиент подделал бы причину: `rejected` или
  `timeout` в теле показались бы собеседнику как «отклонено» или «не ответил».
  `timeout` и `rejected` сервер выставляет сам. Значение из тела не
  ограничено по длине только потому, что принимается одно фиксированное
  значение;
- отправка событий в SSE-хаб и WebPush.

**Атомарность.** Правило и состояние не могут оказаться в разных слоях: индекс
«пользователь → активный звонок» принадлежит менеджеру, значит и проверка
занятости, и создание звонка, и переход `ringing → active` должны выполняться
под мьютексом менеджера одной составной операцией — как реестр соединений в
`sse.Hub`. Иначе два одновременных `POST /api/calls` одному собеседнику
оба прошли бы проверку, а две вкладки, нажавшие «Принять» одновременно, —
обе стали бы звонящими. Менеджер предоставляет атомарные `CreateCall` и
`AcceptCall`; выигравший `accept` отдаёт `answer`, проигравший получает
`409`.

Под мьютексом выполняются только операции с внутренним состоянием менеджера.
Всё, что уходит во внешний код — прежде всего колбэк присутствия, — вызывается
вне блокировки (§4.1).

### 4.3 `transport/calls.go`

| Метод   | Путь                     | Тело                    | Ответ |
|---------|--------------------------|-------------------------|-------|
| `POST`  | `/api/calls`             | `{chatId, offer}`       | `{callId, state}` |
| `POST`  | `/api/calls/{id}/accept` | `{answer}`              | `{state}` |
| `POST`  | `/api/calls/{id}/reject` | —                       | `{state}` |
| `POST`  | `/api/calls/{id}/hangup` | `{reason?}` (необязательно; принимается только `peer-left`, см. §4.2) | `{state}` |
| `POST`  | `/api/calls/{id}/ice`    | `{candidate}`           | `{state}` |
| `GET`   | `/api/calls/current`     | —                       | `{callId, peer, state, role, reason?, endedAt?, offer?, answer?}` |
| `GET`   | `/api/ice`              | —                       | `{stun: [...], turn: [...]}` |

`GET /api/ice` живёт не в `transport/calls.go`, а рядом с `/api/config`
(`transport/users.go`): конфигурация ICE нужна клиенту, но выдавать её можно
только авторизованному пользователю — публичный `/api/config` без
`Security` раздал бы TURN-кред анонимным посетителям (см. §7 и §8).

Коды ответов:

- `401` — нет валидного токена;
- `403` — пользователь не участник чата или не участник звонка; также
  федеративный собеседник (звонки между серверами не поддержаны);
- `404` — звонок не найден или уже завершён; также неизвестный чат;
- `409` — собеседник занят, звонящий сам уже в звонке, звонок уже не в
  `ringing`, или звонок принят в другой вкладке;
- `400` — доменная ошибка в теле (пустой SDP).

Коды доменных ошибок — по конвенции проекта: валидация в сервисном слое с
маппингом через `MapError` в `400` / `403` / `409` (`backend/transport/errors.go`).
Схемных ограничений на тела запросов не вводим — тогда Huma отвечала бы
`422`, чего в проекте сознательно избегают (`backend/transport/auth.go`).

`GET /api/calls/current` отдаёт звонок пользователя: текущий `ringing` (с
offer — чтобы офлайн-принимающий увидел входящий после возвращения) или
`active`; если таких нет — последний завершённый, с полями `reason`,
`endedAt` и `role` (он хранится ещё 10 минут после завершения). Если звонка
нет вообще — `404`.

Завершённый звонок отдаётся с любой причиной, а не только по таймауту: клиент
различает роль звонка по своей фазе и решает, что показать (§6.2). При
`reason: timeout` звонящий видит «не ответил», получатель — «пропущенный
звонок от …»; при `reason: peer-left` получатель видит «собеседник
отключился», а звонящий звонок игнорирует — он и так знает, чем закончилось
(перезагрузил страницу, §9). При `hangup` и `rejected` звонок клиент
игнорирует в обеих ролях.

`role` нужен клиенту, который звонка не вёл: страница, открытая после
завершения, знает только `reason`, и без стороны, на которой был
пользователь, «не ответил» и «пропущенный» неразличимы.

### 4.4 События SSE

Новые события в существующем хабе; маршрутизация — в `useSseEvents`.

| Событие         | Кому   | Данные |
|-----------------|--------|--------|
| `call_incoming` | B      | `{callId, from: {id, nick}, chatId, offer, expiresAt}` |
| `call_accepted` | A      | `{callId, answer}` |
| `call_accepted` | все вкладки B | `{callId}` — без `answer`: вкладкам достаточно, чтобы закрыть окно входящего |
| `call_ended`    | A и B  | `{callId, reason}` |
| `call_ice`      | другая сторона | `{callId, candidate}` |

`call_accepted` получают обе стороны: вызывающий — с `answer`, все вкладки
принимающего — без него. Отдельное событие не нужно: вкладкам, которые не
нажимали «Принять», нужен только `callId`, чтобы закрыть окно.

`call_ended` уходит обеим сторонам во всех случаях — и при `hangup`, и при
таймауте: правило одно, и ни одна сторона не остаётся без уведомления.
Инициатору, который сам повесил трубку, событие безвредно — он и так знает о
своём действии.

**Отказ отдельным событием не выделяется.** При `reject` звонящий получает
тот же `call_ended{reason: rejected}` — терминирующее событие у него ровно
одно, иначе обработчик получил бы два сигнала об одном завершении и
освобождал бы медиа дважды.

`reason` закрытого звонка: `hangup`, `rejected`, `timeout`, `peer-left`.
`timeout` и `rejected` назначает сервер, `peer-left` клиент передаёт сам в
теле `hangup` (§4.2, §4.3) — так собеседник отличит «отключился» от
«повесил трубку». Занятость собеседника — не событие, а ответ `409`
вызывающему: звонок в таком случае не создаётся.

**Push о звонке.** Тег уведомления — `call-<callId>`, а не `chat-<chatId>`
как у сообщений: каждый звонок даёт своё уведомление, и два входящих звонка
подряд не схлопываются в одно. Payload расширяется новым видом —
`{callId, chatId, fromId, fromNick}` (в `PushPayloadData` сейчас только
`ChatID` / `MessageID` / `ThreadID`).

### 4.5 Состояния

```
                 создание
   (нет) ─────────────────────► ringing ──accept──► active ──hangup──► ended
                                 │  ▲                  │                   ▲
                                 │  └──────accept──────┘                   │
                                 │                                        │
                                 ├──reject──► ended ◄────────────────────┘
                                 ├──timeout─► ended
                                 └──caller hangup► ended
```

Занятость: один активный звонок на пользователя. Второй звонок от того же
пользователя или к занятому собеседнику → `409`. Мультитаб: звонок приходит
во все вкладки пользователя; принять может только одна — первый `accept`
выигрывает (переход `ringing → active` атомарен), остальные получают `409` и
закрывают окно по событию `call_accepted` без `answer`, которое приходит тем
же событием всем вкладкам принимающего.

## 5. Протокол сигналинга

1. A: `getUserMedia({audio, video})` → `RTCPeerConnection` → `createOffer` →
   `setLocalDescription` → `POST /api/calls {chatId, offer}`.
2. Сервер: проверки (участник чата, собеседник локальный, B свободен, чат
   1:1) → создаёт звонок (`ringing`, `ExpiresAt = CreatedAt + 45 с`) →
   `call_incoming` с offer → если у B нет живых SSE-соединений (та же
   проверка присутствия, что и для уведомлений о сообщениях), WebPush
   «Входящий звонок от …».
3. A: кандидаты ICE долетают по мере обнаружения через
   `POST /api/calls/{id}/ice` (trickling).
4. B: `call_incoming` → окно входящего → «Принять» → `getUserMedia` →
   `setRemoteDescription(offer)` → `createAnswer` → `setLocalDescription` →
   `POST /api/calls/{id}/accept {answer}`; свои кандидаты — тем же путём.
5. Сервер: `call_accepted` — A с answer, все вкладки B без него → A:
   `setRemoteDescription(answer)` → ICE соединяется → медиа пошли.

Остальные ветки: `reject` → `call_ended{reason: rejected}` у обеих сторон;
`hangup` без тела (любая сторона) → `call_ended{reason: hangup}` у обеих;
`hangup` с `{reason: peer-left}` — так завершает клиент после перезагрузки
страницы — → `call_ended{reason: peer-left}` у обеих; 45 секунд без ответа →
`call_ended{reason: timeout}` у обеих, а получателю звонок остаётся видимым
ещё 10 минут как «пропущенный звонок от …» (без offer — принять его уже
нельзя).

**Офлайн-принимающий и окно ringing.** Вернувшись в пределах 45 секунд,
получатель находит звонок через `GET /api/calls/current` (или получает его
событием `call_incoming`, если SSE успел подключиться) и может принять
звонок с offer. Вернувшись позже, он видит «пропущенный звонок от …» — но
принять его уже нельзя, и вызывающий к этому моменту тоже получил
`call_ended{timeout}`.

## 6. Клиент

### 6.1 Модули

Новая директория `frontend/src/calls/`:

- `callManager.ts` — владеет `RTCPeerConnection` и `getUserMedia`, создаёт
  offer/answer, отправляет и принимает ICE-кандидаты, общается с `api.ts`,
  закрывает звонок по `call_ended`. Закрытие идемпотентно: повторное
  событие с тем же `callId` игнорируется, а потоки освобождаются ровно один
  раз (иначе `track.stop()` вызвался бы дважды);
- `callState.ts` — состояние для интерфейса: фаза
  (`idle | incoming | outgoing | active | ended`), собеседник, `callId`,
  локальный и удалённый потоки, mute/камера, таймер разговора;
- `handleCallEvent.ts` — чистая функция «событие SSE → действие».

`useSseEvents` остаётся единственной точкой входа SSE: он делегирует
события `call_*` в `handleCallEvent`. Второго EventSource не открываем.

Событие дойдёт до обработчика только если оно подписано: список `jsonEvents`
в `frontend/src/useSse.ts` захардкожен, поэтому туда добавляются четыре
события — `call_incoming`, `call_accepted`, `call_ended`, `call_ice`. Без
этого делегирование в `handleCallEvent` не сработает, а событие молча не
придёт: ошибки не будет, отказ обнаружится только в e2e.

### 6.2 Интерфейс

- **Кнопка звонка** в шапке чата (`AppHeader`) — только для приватного чата
  1:1 с другим пользователем и только если собеседник локальный. На
  клиенте локальность определяется равенством доменов в идентификаторах:
  домен сервера берётся из идентификатора самого пользователя
  (`activeAccount.user.id`, вида `nick:домен`), а домен собеседника — из его
  идентификатора. У локального пользователя идентификатор тоже содержит
  домен, поэтому «домен пустой» не подходит. Серверную проверку смотри в
  §4.2.
- **Окно входящего** (`IncomingCallOverlay`): аватар, ник, «Принять» /
  «Отклонить», звук вызова.
- **Экран активного звонка** (`ActiveCallOverlay`): видео собеседника во весь
  экран, своя камера поверх в маленьком превью, кнопки mute / камера /
  завершить, таймер разговора.
- **Индикатор** в шапке и в списке чатов, когда звонок идёт.
- **Завершённый звонок из `/current`**: клиент смотрит на `reason` и на свою
  роль в звонке — фазу из `callState`, если звонок вёл, или `role` из ответа,
  если страница открылась уже после завершения: при `reason: timeout`
  звонящий видит «не ответил», получатель — «пропущенный звонок от …»; при
  `reason: peer-left` получатель видит «собеседник отключился», а звонящий
  звонок игнорирует (он сам перезагрузил страницу и у него уже «звонок
  прерван, перезвоните?»); при `hangup` и `rejected` звонок игнорируется в
  обеих ролях — пользователь и так знает, чем всё закончилось. Клиент,
  открытый после завершения, отчитывается только о `timeout`: остальные
  причины к моменту возвращения уже не новость.

### 6.3 Технические детали

- `<video>` для превью — обязательно `muted` и `playsInline`, иначе Safari не
  проигрывает автозапуск.
- ICE-кандидаты могут прийти раньше `setRemoteDescription`: их нужно
  буферизовать и дослать после (на этом всё обычно и ломается).
- Звонящий: `setLocalDescription(offer)` → ждём ответ →
  `setRemoteDescription(answer)`. Принимающий: `getUserMedia` →
  `setRemoteDescription(offer)` → `createAnswer` → `setLocalDescription(answer)`.
- При завершении обязательно `track.stop()` для всех треков и `pc.close()`,
  иначе камера остаётся включённой.
- Звук вызова генерируется через Web Audio, без бинарных ассетов.

## 7. Конфигурация

Новый блок в YAML:

```yaml
ice:
    stun:
        - stun:stun.l.google.com:19302
    turn:
        - urls: "turn:turn.example.com:3478?transport=udp"
          username: "fastchat"
          credential: "секрет"
```

- `stun` — по умолчанию публичный (в проекте уже есть внешний сервис —
  тайлы OSM).
- `turn` — только если задан. Coturn поднимается отдельно, в репозиторий не
  входит; в README — пример запуска и конфиг.
- Пока TURN не настроен, при старте сервер пишет предупреждение: часть
  сетей (symmetric NAT, мобильные) не соединится.
- Учётные данные TURN — статические, в конфиге. Схема coturn `use-auth-secret`
  (TURN REST API с временными кодами) — на потом.

**Где отдаётся ICE-конфигурация.** Отдельный авторизованный эндпоинт
`GET /api/ice` (Bearer-токен) → `{stun: [...], turn: [...]}`. В публичный
`GET /api/config` он не попадает: тот эндпоинт зарегистрирован без
`Security` (`backend/transport/users.go`), и выдача TURN-креда анонимному
посетителю сделала бы coturn открытым релеем для всех, кто заходит на сайт.

Требование к развёртыванию: `getUserMedia` работает только по HTTPS (кроме
`localhost`). Сервер один раз за процесс пишет предупреждение, если увидел
запрос без TLS (за обратным прокси — по `X-Forwarded-Proto` от доверенного
прокси): в такой публикации звонок в браузере не заработает.

## 8. Безопасность и приватность

- Звонок доступен только участникам одного приватного чата 1:1; проверка на
  сервере в каждом эндпоинте, а не только при создании.
- Собеседник должен быть локальным: федеративный собеседник отклоняется с
  `403`.
- Доступ к эндпоинтам звонка — только участники самого звонка.
- `callId` — 128 бит случайных байт, не подбирается.
- SDP и ICE-кандидаты не логируются: в них внутренние IP-адреса. Текущий
  request-log пишет только method/path/status — это правило соблюдается в
  новом коде.
- В P2P без TURN собеседники видят IP друг друга; с TURN — нет. Указано в
  документации.
- CORS и авторизация — те же, что у остального API (Bearer-токен).
- **TURN со статическим паролем**: даже через авторизованный `GET /api/ice`
  код уходит в браузер любого зарегистрированного пользователя, то есть
  coturn становится релеем для всех, кто может зайти на сайт. Поэтому при
  старте с настроенным TURN и статическим паролем сервер пишет громкое
  предупреждение. Схема coturn `use-auth-secret` (TURN REST API с
  короткоживущими кодами) снимает риск — это следующий шаг.
- **Push раскрывает факт звонка**: уведомление содержит ник звонящего и
  `callId`. Это ожидаемо для мессенджера, но учитывается при выборе
  показателя «звонки отключены».

## 9. Ошибки и краевые случаи

| Ситуация | Поведение |
|----------|-----------|
| Собеседник офлайн | Push; вернувшись в пределах окна ringing (45 с), он находит звонок через `GET /api/calls/current` и может его принять (в payload есть offer); вернувшись позже — видит «пропущенный звонок от …» (`state: ended`, `reason: timeout`, без offer), принять уже нельзя |
| Перезагрузка страницы (F5) во время звонка | `callId` лежит в `sessionStorage`; при старте клиент шлёт `hangup` с `{reason: peer-left}` → собеседник видит `call_ended{peer-left}`, а пользователь — «звонок прерван, перезвоните?» |
| Несколько вкладок | Входящий приходит во все; принять может одна (первый `accept`, переход атомарен), остальные получают `409` и закрывают окно по `call_accepted` без `answer` |
| Нет камеры | `getUserMedia` падает `NotFoundError` → предлагаем звонок только со звуком; нет и звука → ошибка, звонок не начинается |
| Микрофон занят | `NotReadableError` → понятное сообщение, звонок не начинается |
| Собеседник занят | `409` → «собеседник занят» |
| Звонящий сам уже в звонке | `409` с отдельным сообщением «вы уже в звонке»; кнопка звонка в интерфейсе неактивна |
| Федеративный собеседник | `403` «звонки между серверами не поддержаны»; кнопки звонка в чате нет |
| Нет ответа 45 с | `call_ended{timeout}` у обеих сторон; получателю звонок остаётся видимым 10 минут как «пропущенный» |
| Оборвалась сеть во время звонка | Медиа P2P не зависит от сервера и продолжает идти; клиент переподключает SSE и сверяется с `GET /api/calls/current` |
| Клиент пропал насовсем (падение браузера, закрытая вкладка) | Присутствие пропадает вместе с SSE; после минуты простоя уборщик завершает звонок с `peer-left`, и собеседник освобождается, а не ждёт жёсткого TTL в 4 часа |
| Звонок в группу или self-чат | Кнопки нет, сервер отвечает `400` |

## 10. Тестирование

**Backend unit-тесты:**

- `calls`: переходы состояний, таймаут 45 с, занятость, TTL-уборщик (в том
  числе снятие зависшего активного звонка по колбэку присутствия и по
  жёсткому TTL), очистка SDP при переходе в `ended`, уборка записи через
  10 минут после `ended`;
- `service/calls.go`: нельзя звонить не-участнику, в self-чат, себе,
  федеративному собеседнику; занятый собеседник → `409`; звонящий сам в
  звонке → `409`; `accept` не из того чата → `403`; второй `accept` → `409`;
  неизвестный `reason` в теле `hangup` отбрасывается, причина остаётся
  `hangup` (клиент не может подделать `rejected` или `timeout`);
- `calls`: уборщик не вызывает колбэк присутствия под мьютексом — проверка
  идёт по снимку «кто офлайн», взятому до блокировки;
- `transport/calls.go`: `401` без токена, `404` на чужой `callId`, `400` на
  пустой SDP, `403` на федеративного собеседника, `reason` из тела `hangup`
  попадает в `call_ended` только в значении `peer-left`.

**Frontend unit-тесты (vitest + jsdom):** `callManager` с подменённым
`RTCPeerConnection` — порядок `createOffer` / `createAnswer` /
`setRemoteDescription`, буферизация ICE-кандидатов, пришедших раньше времени,
очистка (`track.stop()`, `pc.close()`) ровно один раз при повторном
`call_ended`, обработка `call_ended`; `handleCallEvent` — маршрутизация; UI —
кнопка только в чате 1:1, окна входящего и активного звонка.

**Playwright e2e:** два контекста в одном браузере с фейковыми камерами и
микрофонами (`--use-fake-device-for-media-stream`). Сценарии: принятие
звонка (проверяем, что удалённый видеотрек пришёл: `videoWidth > 0`),
отклонение, занятость, завершение. Прямое соединение идёт по
host-кандидатам loopback, TURN для тестов не нужен.

Два практических момента:

- vitest по умолчанию подхватывает `*.spec.ts` — e2e-тесты называем
  `*.e2e.ts` и исключаем из vitest, иначе vitest запустит Playwright-тесты
  и упадёт;
- e2e требует живого стенда: в CI — отдельный джоб, который поднимает
  бэкенд и собранный фронтенд, ставит браузеры Playwright и гоняет сценарии.
  Это самая рискованная часть (гонки и таймауты), начинать с неё стоит рано.

## 11. Порядок работ

1. Конфиг `ice:` + авторизованный эндпоинт `GET /api/ice` + предупреждения
   в логах (нет TURN, задан TURN со статическим паролем, публикация без
   TLS).
2. Backend: пакет `calls` (реестр, атомарные `CreateCall` / `AcceptCall`,
   колбэк присутствия `OfflineSince` для уборщика зависших звонков, генерация
   id через `internal/ids`, чтобы пакет не зависел от `store`) →
   `service/calls.go` → `transport/calls.go`. В `shutdown` — `calls.Close()`
   строго до `sse.Hub.Close()`, иначе `call_ended` не уйдёт никому.
3. Frontend: `callManager` → `callState` → `handleCallEvent` → подключение
   к `useSseEvents` **и** расширение списка `jsonEvents` в
   `frontend/src/useSse.ts` четырьмя событиями `call_*` (без этого события
   не доходят до обработчика).
4. UI: кнопка в шапке, окно входящего, экран активного звонка, показ
   пропущенного звонка.
5. Unit-тесты (backend + frontend) по ходу работы, а не в конце.
6. Playwright e2e + джоб в CI.
7. README: раздел «Звонки», пример coturn, требование HTTPS, ограничения
   MVP.

## 12. Принятые решения и допущения

Решения, принятые на этапе обсуждения:

- медиа — P2P, coturn как запасной путь;
- только внутри одного сервера, федерация и SFU — потом;
- состояние звонка — в памяти процесса;
- полная модель вызова: звонящий/принимающий, отклонение, отмена,
  занятость, таймаут;
- аудио и видео сразу;
- сигналинг через существующий SSE и REST, без WebSocket;
- e2e на Playwright с двумя браузерами — в этом же наборе;
- оффлайн-принимающий: принять можно в пределах окна ringing (45 с), позже
  он видит «пропущенный звонок»;
- ICE-конфигурация — в отдельном авторизованном эндпоинте `GET /api/ice`;
- терминирующее событие одно — `call_ended` с `reason`; отказ отдельным
  событием не выделяется, чтобы у звонящего не было двух сигналов об одном
  завершении;
- уборщик зависших активных звонков опирается на колбэк присутствия
  `OfflineSince` (подключается к `store.OfflineSince`) и на жёсткий TTL как
  страховку.

Допущения, которые стоит проверить на практике:

- `getUserMedia` в PWA на iOS Safari 16.4+ работает по HTTPS; на более
  старых версиях звонок из PWA не заработает;
- fake-медиа Playwright даёт реальные видеотреки, достаточные для проверки
  приёма звонка;
- публичный STUN доступен из большинства сетей; если нет — нужен свой.

Открытых вопросов, блокирующих реализацию, нет.
