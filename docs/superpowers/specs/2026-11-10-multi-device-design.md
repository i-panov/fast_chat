# Мультидевайс: независимые сессии и E2EE — дизайн

Дата: 2026-11-10
Статус: исторический документ. Актуальная реализация — v3: один мастер-ключ
на аккаунт (X25519 + Ed25519), один конверт на участника с `keyVersion`,
парольный/passkey-бэкап. Phase B с отдельным ключом на устройство и
per-device backup/UI **не реализована и удалена**; `user_devices` остались
только как legacy-строки для списка устройств.
Область: одновременный вход одного аккаунта с нескольких устройств,
управление сессиями и сохранение E2EE при нескольких устройствах.

Группы, coturn и федеративные вложения — отдельные спеки. Здесь их нет.

## 1. Контекст

Сейчас у аккаунта **одна сессия**: токен хранится в `users.token`, а вход
на втором устройстве вызывает `RefreshUserToken` и перезаписывает его.
Первое устройство получает `401` и выкидывается. Это видно в
`backend/store/users.go`, `backend/service/auth.go` и
`backend/transport/auth.go`.

E2EE тоже рассчитан на один ключ аккаунта:

- у аккаунта один X25519-ключ;
- публичный ключ один на пользователя;
- в зашифрованном сообщении конверт ключа адресован `keyId = userId`;
- приватный ключ хранится в IndexedDB конкретного браузера.

Из-за этого новое устройство без локального ключа либо восстанавливает
ключ из бэкапа, либо генерирует новый и ломает чтение старых сообщений.

## 2. Цель

1. Один аккаунт может быть одновременно авторизован на нескольких
   устройствах.
2. У каждого устройства своя сессия: свой токен, свой срок жизни, свой
   отзыв.
3. Пользователь видит список устройств и может отозвать любую сессию или
   выйти на всех устройствах.
4. Все существующие функции работают при нескольких устройствах:
   сообщения, SSE, push, звонки, typing, read receipts, sync, outbox.
5. E2EE не ломается при входе на новом устройстве.

## 3. Границы

Входит:

- таблица сессий и миграция с `users.token`;
- API входа, refresh, logout, список и отзыв сессий;
- SSE на сессию, presence, push на устройство, звонки на все устройства;
- E2EE-вариант «один ключ аккаунта + обязательное восстановление из
  бэкапа»;
- frontend: device ID, список устройств, отзыв, согласование refresh
  между вкладками;
- тесты backend/frontend/e2e.

Не входит (следующие этапы):

- отдельный ключ на каждое устройство (Phase B, см. §11);
- device pairing/QR-код и перенос ключа между устройствами;
- удалённое стирание данных устройства;
- отдельные read receipts/typing по устройствам;
- несколько одновременных звонков на аккаунт (звонок остаётся один);
- изменения федеративного протокола: сессии локальны для сервера.

## 4. Решения

- **D1. Сессия — отдельная сущность.** Токен больше не принадлежит
  пользователю, а принадлежит сессии. В БД хранится только хэш токена.
- **D2. Одно активное устройство = одна сессия.** Клиент генерирует
  `deviceId` и присылает его при входе. Повторный вход на том же устройстве
  заменяет сессию этого устройства, а не создаёт вторую.
- **D3. Session ID стабилен, токен ротируется.** При refresh меняется
  только токен и срок жизни; `sessionId` остаётся прежним.
- **D4. Phase A E2EE — один ключ аккаунта.** Все устройства используют один
  и тот же приватный ключ, полученный из серверного бэкапа. Новое
  устройство не должно молча генерировать новый ключ.
- **D5. Phase B — ключ на устройство.** Отдельная задача: новый формат
  конвертов, регистрация устройств, отзыв ключей. В этой спеке только
  задел.
- **D6. Федерации сессии не касаются.** Удалённые серверы не знают о
  сессиях; они по-прежнему видят только `userId`. Менять федеративные
  заголовки не нужно.

## 5. Модель данных

### 5.1. Session

Новая модель `model.Session`:

```go
type Session struct {
    ID         string     `gorm:"primaryKey"`
    UserID     string     `gorm:"uniqueIndex:idx_sessions_user_device;not null"`
    DeviceID   string     `gorm:"uniqueIndex:idx_sessions_user_device;not null"`
    DeviceName string     `gorm:"not null;default:''"`
    TokenHash  string     `gorm:"uniqueIndex;not null"`
    UserAgent  string     `gorm:"not null;default:''"`
    CreatedAt  time.Time  `gorm:"not null"`
    LastSeenAt time.Time  `gorm:"not null"`
    ExpiresAt  time.Time  `gorm:"index;not null"`
    RevokedAt  *time.Time `gorm:"index"`
}
```

Индексы:

- `token_hash` — уникальный, поиск при каждом запросе;
- `(user_id, device_id)` — уникальный: одно активное устройство = одна
  сессия;
- `user_id`, `expires_at`, `revoked_at` — для списка и очистки.

Правила:

- `ID` — случайный 128-битный идентификатор, генерируется сервером;
- `DeviceID` — случайный UUID, генерируется клиентом и хранится в
  `localStorage`; для старых клиентов сервер создаёт `legacy-<random>`;
- `DeviceName` — человекочитаемое имя, присылает клиент, максимум 64
  символа; сервер не доверяет ему и только экранирует при выводе;
- `TokenHash = SHA-256(plain token)`; plaintext-токен возвращается клиенту
  один раз;
- `ExpiresAt` — скользящий срок: refresh продлевает;
- `RevokedAt != nil` — сессия отозвана и не проходит аутентификацию;
- `LastSeenAt` обновляется на refresh и не чаще одного раза в 5 минут на
  запросах/SSE.

### 5.2. PushSubscription

Добавить `SessionID string` с индексом. Подписка на push принадлежит
устройству/сессии, а не только пользователю.

- при подписке сервер берёт текущую сессию из контекста;
- `UNIQUE(endpoint)` сохраняется; повторная подписка обновляет
  `session_id`;
- при logout/revoke сессии удаляются только её подписки;
- старые подписки без `session_id` считаются legacy: push по ним
  отправляется только если пользователь полностью offline, и они
  заменяются при следующем запуске приложения.

### 5.3. users.token и users.token_expires_at

Источник истины — `sessions`. Аутентификация (`AuthMiddleware`,
`GetSessionByToken`, SSE heartbeat) читает только `sessions` и никогда не
проверяет `users.token`.

`users.token` и `users.token_expires_at` остаются на один релиз как
legacy-зеркало для совместимости со старой схемой и отката:

- `CreateSession` и `RefreshSession` в той же транзакции, что и изменение
  сессии, записывают в зеркало хэш и срок только что созданной/обновлённой
  сессии;
- `RevokeSession` и `RevokeAllSessions` инвалидируют зеркало: пишут случайный
  хэш и текущее время, чтобы после рестарта старая база не «воскресила»
  сессию из `users.token`;
- `CreateUserWithSession` (регистрация) создаёт пользователя и его первую
  сессию в одной транзакции; `users.token` заполняется тем же хэшем, что и
  `session.token_hash`, а plaintext-токен возвращается клиенту один раз.

Зеркало не даёт доступа: если в `sessions` нет соответствующей активной
строки, `users.token` игнорируется. Удаление колонок — отдельным релизом.

### 5.4. Лимит сессий

Новая настройка `auth.max_sessions_per_user`, по умолчанию 50. `0`
трактуется как значение по умолчанию 50, отрицательное значение невалидно;
безлимитный режим сейчас не поддерживается. При превышении лимита
отзывается самая старая сессия, кроме текущей. Это защита от бесконечного
роста, а не продуктовое ограничение.

Лимит применяется при входе: после логина (создания или обновления сессии
устройства) `trimSessions` отзывает самые старые сессии сверх лимита (кроме
текущей), закрывает их SSE-соединения и удаляет их push-подписки. Отозванная
по лимиту сессия получает `401` на следующий refresh.

Фоновый cleanup раз в час удаляет сессии, у которых `expires_at` или
`revoked_at` старше 30 дней. Он не трогает активные сессии и не влияет на
токены, которые ещё могут понадобиться для аудита.

## 6. Аутентификация и API

### 6.1. Общие правила

- Токен — 128-битный random, 32 hex-символа, как сейчас (`ids.Generate`).
- Наружу токен отдаётся только в ответе на login/refresh.
- В БД — только SHA-256.
- Все операции над сессиями — только для своего `userId`.
- `401` — токен неизвестен, сессия отозвана или истекла.
- `404` — чужая/несуществующая сессия при отзыве.

### 6.2. Вход существующего пользователя

`POST /api/auth/verify-code`

Запрос:

```json
{
  "email": "a@example.com",
  "code": "123456",
  "deviceId": "uuid",
  "deviceName": "Chrome on Linux"
}
```

Ответ:

```json
{
  "isNew": false,
  "user": { "id": "alice:localhost:8080", "nick": "alice", "online": true },
  "token": "plain-token",
  "expiresAt": "2026-11-11T12:00:00Z",
  "sessionId": "session-id",
  "deviceId": "uuid"
}
```

Поведение:

- для пары `(userId, deviceId)` ищется существующая сессия;
- если она есть — обновляются токен, срок, `user_agent`, `device_name`,
  `revoked_at = nil`;
- если нет — создаётся новая;
- другие сессии пользователя не трогаются. **Это ключевое отличие от
  текущего поведения.**
- если `deviceId` не передан, сервер генерирует `legacy-<random>` и
  возвращает его; клиент сохраняет.

### 6.3. Регистрация

`POST /api/auth/complete-registration`

Запрос получает `setupToken`, `nick`, `deviceId?`, `deviceName?`.
Пользователь и первая сессия создаются в одной транзакции. Ответ — как у
`verify-code`, плюс `user`.

### 6.4. Refresh

`POST /api/auth/refresh-token`

- Находит сессию по текущему токену.
- Проверяет, что она не отозвана и не истекла.
- Генерирует новый токен, обновляет `token_hash`, `expires_at`,
  `last_seen_at`.
- Возвращает `{token, expiresAt, sessionId}`.
- Старый токен сразу перестаёт работать.
- Другие сессии не затрагиваются.

### 6.5. Logout

`POST /api/auth/logout` — отзывает **только текущую сессию**:

- `revoked_at = now`, `expires_at = now`;
- `token_hash` заменяется на хэш случайного значения, чтобы старый токен
  не мог совпасть;
- закрываются SSE-соединения этой сессии;
- удаляются push-подписки этой сессии.

`POST /api/auth/logout-all` — то же для всех сессий пользователя. Закрывает
все SSE (`Hub.CloseUserSessions(userID)`) и удаляет все push-подписки.

### 6.6. Список и отзыв устройств

`GET /api/sessions`

```json
{
  "currentSessionId": "s1",
  "sessions": [
    {
      "id": "s1",
      "deviceId": "uuid-1",
      "deviceName": "Chrome on Linux",
      "userAgent": "...",
      "createdAt": "...",
      "lastSeenAt": "...",
      "expiresAt": "...",
      "current": true
    }
  ]
}
```

`DELETE /api/sessions/{id}` — отзывает выбранную сессию (кроме текущей:
для текущей клиент использует logout). Закрывает SSE и удаляет push этой
сессии.

Для «выйти на всех» используется `POST /api/auth/logout-all` из §6.5.

### 6.7. Middleware

`AuthMiddleware`:

- ищет сессию по `token_hash`, а не пользователя по токену;
- проверяет `revoked_at == nil` и `expires_at > now`;
- загружает пользователя по `user_id`;
- кладёт в контекст `authUser{ID, Nick, SessionID, DeviceID}`;
- `userFromContext` остаётся для существующих хендлеров, добавляется
  `sessionFromContext`.

`GetUserByToken` заменяется на `GetSessionByToken`, который возвращает
сессию и пользователя. Старые вызовы (`sse-auth`, heartbeat) переводятся
на него.

### 6.8. Refresh и несколько вкладок

Ротация токена создаёт гонку между вкладками одного устройства: обе
могут одновременно вызвать refresh, и вторая затрёт токен первой.

Правила frontend:

- refresh выполняется под `navigator.locks.request("fastchat-refresh-<session>")`,
  если Web Locks доступен;
- после refresh новый токен пишется в `localStorage` и рассылается через
  `BroadcastChannel("fastchat-auth")`;
- при `401` вкладка сначала перечитывает аккаунты из `localStorage`; если
  там уже новый токен, запрос повторяется один раз;
- только после этого аккаунт удаляется и показывается логин.

Fallback без Web Locks: короткий lease в `localStorage` с timestamp; при
конфликте — повторное чтение токена и один retry.

## 7. SSE

Соединение привязывается к сессии, а не к пользователю.

Изменения:

- `sse.Connection` получает `SessionID`;
- `sse-auth` валидирует токен через `GetSessionByToken`, передаёт в hub
  `userID`, `sessionID`, `expiresAt`;
- `sse-auth` идемпотентен: повторная аутентификация того же
  `connectionId` не увеличивает счётчик presence второй раз;
- `Store.AddConnection(userID, sessionID)` и
  `RemoveConnection(userID, sessionID)` считают соединения и по
  пользователю, и по сессии;
- `Hub.CloseSession(sessionID)` закрывает все соединения сессии
  (несколько вкладок — несколько соединений);
- `Hub.UpdateSessionExpiry(sessionID, expiresAt)` вызывается после refresh,
  чтобы открытый SSE не умер от старого срока;
- heartbeat проверяет сессию по `sessionID` (отозвана/истекла), а не
  токен; ротация токена не рвёт поток;
- presence остаётся на уровне пользователя: online, если есть хотя бы одно
  соединение любой сессии; offline-событие — когда закрылось последнее;
- logout/revoke сессии немедленно закрывает её SSE; если это была
  последняя сессия, уходит `online=false`.

Если сессию отозвали, а SSE-соединение почему-то не закрылось, heartbeat
закроет его не позже 30 секунд.

## 8. Push

Push становится per-session.

- `POST /api/push/subscribe` берёт `sessionId` из контекста и сохраняет
  подписку с этой сессией.
- `DELETE /api/push/subscribe` удаляет подписку только текущей сессии.
- `logout`/`logout-all`/`revoke` удаляют соответствующие подписки.
- `IsSessionOnline(sessionID)` — есть ли SSE этой сессии.
- Для нового сообщения:
  - по каждому получателю берутся все подписки;
  - подписка пропускается, если её сессия online;
  - legacy-подписка без `session_id` пропускается, если пользователь
    online (старое поведение);
  - остальным отправляется push.
- Для входящего звонка — то же: online-устройства получают SSE
  `call_incoming`, offline-устройства — push.
- `maxPushSubscriptionsPerUser = 20` пока остаётся; при нескольких
  устройствах это нормальный запас. Позже можно поднять.

Смысл: если у пользователя телефон online, а ноутбук offline, сообщение
придёт на телефон по SSE, а на ноутбук — push. Сейчас в такой ситуации
push не уходит вообще, потому что `IsOnline(userID)` истинно.

## 9. Звонки

Звонок остаётся **один на аккаунт**, а не на устройство.

- `call_incoming` уходит всем online-сессиям пользователя;
- пользователь принимает на одном устройстве;
- сервер шлёт `call_accepted` без `answer` всем соединениям callee;
  принявшее устройство продолжает, остальные закрывают окно
  (`taken-elsewhere` уже реализовано в `callManager`);
- reject/hangup завершает звонок для всех устройств;
- `GET /api/calls/current` возвращает общий звонок аккаунта;
- push о входящем — только offline-сессиям (см. §8);
- `call_ice` уходит всем сессиям, но применяет его только та, у которой
  есть активное peer connection; остальные игнорируют событие по
  `callId`.

Второе устройство **не входит** в уже идущий звонок: это 1:1 WebRTC, и
второй peer connection к тому же собеседнику не создаётся. Устройство
видит, что звонок занят/идёт на другом устройстве, и не предлагает
присоединиться. Это осознанно вне рамок: для «продолжить на другом
устройстве» нужен transfer/handoff, отдельная задача.

Код звонков в основном уже готов к этому: SSE fan-out идёт на
пользователя, а не на одно соединение. Меняется push-фильтр и тесты.

## 10. E2EE: Phase A — общий ключ аккаунта

### 10.1. Решение

На этом этапе у аккаунта **один ключ**, как сейчас. Все устройства должны
использовать один и тот же приватный ключ. Новое устройство получает его
из серверного бэкапа, зашифрованного паролем.

Плюсы: не меняется формат сообщений, старые сообщения читаются на всех
устройствах, меньше работы.
Минусы: компрометация одного устройства компрометирует все; отзыв сессии
не отзывает криптоключ; удалённо стереть ключ с потерянного устройства
нельзя. Это осознанный компромисс Phase A; Phase B его снимает.

### 10.2. Что меняется в клиенте

`ensureAccountKeys` сейчас:

- если локальный ключ есть — использует его;
- если ключа нет и есть бэкап — выбрасывает `RecoveryRequiredError`;
- если ключа нет и бэкапа нет — генерирует новый ключ.

Новое поведение:

1. Локальный ключ есть — используем, ничего не меняем.
2. Ключа нет, серверный бэкап есть — показываем RecoveryModal и требуем
   восстановление. Без восстановления E2EE-операции заблокированы.
3. Ключа нет, бэкапа нет, у аккаунта есть другие активные сессии —
   **запрещаем генерировать новый ключ**. Показываем экран:
   «Настройте резервную копию на другом устройстве или выйдите на всех
   устройствах». Это защищает другие устройства от поломки.
4. Ключа нет, бэкапа нет, других активных сессий нет — разрешаем создать
   новый ключ только после явного подтверждения с предупреждением, что
   старые сообщения останутся нечитаемыми.

Для шага 3 клиент запрашивает `GET /api/sessions` и смотрит, есть ли
сессии кроме текущей (`current: true` — текущая, остальные — другие
устройства).

### 10.3. Бэкап

- Бэкап остаётся один на аккаунт: `users.key_backup`.
- Пароль и PBKDF2 не меняются.
- После восстановления публичный ключ тот же; повторная загрузка
  публичного ключа безопасна.
- Если пользователь создал новый ключ (шаг 4), публичный ключ меняется;
  другие устройства увидят новый `keyVersion` после истечения кэша
  публичных ключей (5 минут) и начнут шифровать новым ключом. Старые
  сообщения на них останутся читаемыми, новые — только на устройствах с
  новым ключом. Поэтому шаг 4 разрешён только без других сессий.

### 10.4. UX

- При первом входе на новом устройстве показываем не пустой чат, а экран
  восстановления ключа, пока ключ не получен.
- В настройках аккаунта — напоминание создать бэкап, если его нет.
- Если бэкап есть, но пароль забыт — доступен только сценарий «начать с
  нового ключа» после logout-all; старые сообщения теряются.

## 11. E2EE: Phase B — ключ на устройство (задел)

Отдельная спека, не входит в эту реализацию.

Кратко:

- таблица `user_devices`: `id`, `user_id`, `public_key`, `created_at`,
  `revoked_at`, `last_seen_at`;
- сообщение получает формат `v2`: конверт ключа сообщения на каждое
  активное устройство каждого участника, `keyId = deviceId`;
- отправитель шифрует ключ сообщения всем устройствам, включая свои;
- получатель ищет конверт своего `deviceId`; старые сообщения с
  `keyId = userId` читаются как legacy;
- отзыв устройства исключает его из будущих сообщений;
- новое устройство читает только новые сообщения; историю можно получить
  только через перенос ключа старого устройства или отдельный бэкап;
- нужен федеративный endpoint для публичных ключей устройств.

Причины отложить: миграция формата сообщений, поведение истории на новом
устройстве, UI отзыва устройств и совместимость со старыми клиентами.

## 12. Frontend

### 12.1. Хранение

`StoredAccount` расширяется:

```ts
{
  token: string;
  sessionId: string;
  deviceId: string;
  deviceName: string;
  user: { id: string; nick: string };
  email: string;
  expiresAt: string;
}
```

`deviceId` создаётся один раз и хранится в `localStorage` под отдельным
ключом (не в аккаунте). `deviceName` вычисляется из `navigator.userAgent`
или `navigator.platform`; максимум 64 символа.

Старые аккаунты в `localStorage` не имеют `sessionId`. При первом запуске
после обновления фронтенд вызывает `GET /api/sessions` и сохраняет
`currentSessionId` в активный аккаунт. Если запрос не удался, `sessionId`
остаётся пустым до следующего успешного refresh; список устройств в этом
случае попросит повторить.

### 12.2. Экраны

- В `AccountSwitcher` или настройках — пункт «Устройства».
- Модалка со списком: имя устройства, браузер/ОС, создана, последняя
  активность, «это устройство».
- Кнопка «Отозвать» у других сессий; подтверждение.
- Кнопка «Выйти на всех устройствах».
- После отзыва текущей сессии — переход на логин.

### 12.3. Refresh и 401

- `useAuth` оборачивает refresh в Web Locks.
- После refresh обновляет `StoredAccount` и рассылает событие через
  `BroadcastChannel`; другие вкладки обновляют токен без перезагрузки.
- `onUnauthorized(token)` перед удалением аккаунта перечитывает
  `localStorage`: если токен уже заменён, повторяет запрос; иначе удаляет
  только этот аккаунт.
- SSE переподключается после смены токена; сервер также обновляет expiry
  сессии в hub.

### 12.4. Push

- Подписка создаётся после логина; сервер привязывает её к текущей сессии.
- При logout текущей сессии — `unsubscribe` для её endpoint.
- При logout-all — сервер удаляет все подписки.
- После revoke сессии push на это устройство больше не приходит.

## 13. Миграция и rollout

### 13.1. Миграция

1. AutoMigrate `Session`, добавить `PushSubscription.SessionID`.
2. Backfill: для каждого пользователя с непустым `users.token` и сроком в
   будущем проверяется, есть ли у него хотя бы одна строка в `sessions`.
   - Если строк нет — создаётся legacy-сессия:
     - `id` — новый;
     - `user_id` — пользователь;
     - `device_id` — `legacy`;
     - `device_name` — `Legacy session`;
     - `token_hash` — существующий `users.token` (он уже хэш);
     - `expires_at` — `users.token_expires_at`;
     - `created_at`/`last_seen_at` — now.
   - Если есть хотя бы одна строка — активная, отозванная или legacy —
     пользователь пропускается: `sessions` авторитетна, а `users.token`
     игнорируется. Это исправление «воскрешения» сессии после рестарта:
     после refresh хэш в `users.token` может быть устаревшим, а после revoke
     — оставаться непустым.
3. Backfill push: существующие подписки получают `session_id = ''`
   (legacy). При следующем запуске клиент переподпишется с текущей
   сессией.
4. `users.token`/`token_expires_at` — legacy-зеркало: новый код пишет их при
   создании и refresh сессии и инвалидирует при revoke, но никогда не
   аутентифицирует по ним. Колонки остаются.
5. Отдельным релизом — удалить `users.token`/`users.token_expires_at` и
   их индексы.

### 13.2. Порядок

1. Backend: модель, store, миграция, middleware, API.
2. Backend: SSE, push, presence, звонки.
3. Frontend: deviceId, sessionId, список устройств — реализовано.
   Cross-tab refresh-координация (Web Locks/BroadcastChannel) — реализовано.
4. Frontend: E2EE guard (общий ключ, запрет молчаливого нового ключа) —
   реализовано.
5. Тесты и e2e в двух браузерах — реализовано
   (`frontend/e2e/multi-device.e2e.ts`).
6. Только потом — Phase B (ключи на устройство).

### 13.3. Откат

Откат на код до сессий — односторонний и не сохраняет все устройства. Старый
бинарник смотрит только на `users.token`, а туда после обновления попадает
лишь одна сессия — последняя созданная или обновлённая — и только до первого
logout/revoke: `RevokeSession`/`RevokeAllSessions` инвалидируют зеркало
(пишут случайный хэш и текущее время). Поэтому старый код увидит не более
одного устройства, а после logout-all старые токены не восстановятся.

Сессии, созданные после обновления, старый бинарник не понимает: он не
читает `sessions`. Откат — одномоментный, с потерей дополнительных сессий;
это нужно указать в release notes.

## 14. Безопасность

- Токен 128 бит, хэш SHA-256; plaintext не логируется.
- Ротация токена при refresh; отзыв немедленный.
- `revoke` закрывает SSE и удаляет push.
- Список сессий отдаётся только владельцу.
- `deviceName` — недоверенный ввод: ограничение длины, экранирование,
  никакого HTML.
- IP-адрес не привязываем: мобильные сети меняют его; для отображения
  можно хранить только `user_agent`.
- CSRF не применим: Bearer-токен, не cookie.
- XSS остаётся главным риском: токены в `localStorage` — существующий
  компромисс; новых секретов туда не добавляем.
- Лимит сессий — защита от роста; отзыв самой старой при превышении.
- `auth.max_sessions_per_user` и `auth.token_expiry` валидируются в
  конфиге.

## 15. Тесты

### Backend

- store: create/list/revoke/expire session; поиск по токену; уникальность
  `(user_id, device_id)`; hash не равен plaintext.
- auth: второй login не отзывает первый; refresh одной сессии не ломает
  другую; logout одной не трогает другую; logout-all отзывает все.
- middleware: старый токен после второго login работает; отозванный —
  401; истёкший — 401; чужая сессия — 404.
- SSE: две сессии получают события; revoke закрывает только одну;
  presence остаётся online, пока есть другая; heartbeat видит revoke;
  refresh продлевает.
- push: online-устройство не получает push, offline получает; logout
  удаляет только свои подписки; legacy-подписка ведёт себя по-старому.
- calls: обе сессии получают `call_incoming`; accept на одной закрывает
  вторую; reject/hangup завершает у всех; push только offline.
- migration: старая БД с `users.token` → сессия создана, старый токен
  работает.

### Frontend

- deviceId создаётся один раз; sessionId сохраняется.
- список устройств, revoke, logout-all.
- refresh под Web Locks; вторая вкладка получает новый токен.
- 401 со старым токеном не удаляет аккаунт, если токен уже обновлён.
- E2EE: новый девайс без ключа показывает recovery; без бэкапа и с
  другой сессией — блокирует новый ключ; без других сессий — требует
  подтверждение.
- push subscribe/unsubscribe привязаны к сессии.

### E2E

- Два браузерных контекста, один аккаунт: сообщения и звонки работают в
  обе стороны.
- Отзыв сессии в одном контексте: второй продолжает работать.
- Logout-all: оба контекста разлогинены.
- Reload с активным звонком по-прежнему завершает звонок у обоих.

## 16. Критерии приёмки

- [ ] Можно войти с двух устройств одновременно.
- [ ] Второй вход не выкидывает первое устройство.
- [ ] Список устройств показывает оба; можно отозвать любое.
- [ ] Отзыв одной сессии не влияет на другую.
- [ ] Refresh одной сессии не влияет на другую.
- [ ] Сообщения/SSE/typing/read receipts работают на обоих устройствах.
- [ ] Push приходит на offline-устройство, даже если второе online.
- [ ] Звонок звонит на оба устройства; accept на одном закрывает второе.
- [ ] Logout-all завершает все сессии и закрывает SSE/push.
- [ ] Новое устройство восстанавливает ключ из бэкапа; старые сообщения
      читаются.
- [ ] Без бэкапа и при наличии других сессий новый ключ не генерируется.
- [ ] Старый токен из предыдущей версии продолжает работать после
      миграции.
- [ ] `make lint` и `make test` зелёные; e2e с двумя контекстами зелёный.
