# E2EE for external bots

Status: implemented on payload v3 (master key + Ed25519 identity), including
encrypted inline keyboards, callback data and federated bot chats. The
remaining gaps are listed at the end.

> Исторический документ: описание ниже писалось до перехода на v3. Актуальный
> контракт — одна пара X25519 (`publicKey`) и одна пара Ed25519
> (`identityPublicKey`), клиентский `id` сообщения обязателен для
> зашифрованной отправки, v1/v2 отклоняются.

A bot switches to E2EE with `PUT /api/bot-api/encryption-key`; bot chats start
in `server` mode and are plaintext until that call.

## Threat model

Protected from: the Fast Chat server, its database, backups and federation
peers.

Not protected from: the bot itself, its host, or metadata (who talks to whom,
timestamps, message sizes). The root bot is server-side and cannot be E2EE
against the server.

## Key registration

- The bot generates an X25519 key pair for envelopes and an Ed25519 identity
  pair for sender signatures.
- `PUT /api/bot-api/encryption-key` accepts both public halves, stores them on
  the bot's `users.public_key` / `users.identity_public_key`, and switches
  `bots.encryption_mode` to `e2ee`.
- The private keys stay on the bot host. The server never receives them.
- Re-enabling with the same identity may rotate the encryption key and bumps
  `key_version`; a different identity returns `409` because peers pinned the
  old one. There is no automatic bot key history: rotate in idle time.

## User to bot

- The client sees `ChatView.botEncryptionMode == "e2ee"` and does not take the
  plaintext bot-chat path.
- It fetches the bot public key from the normal user-key endpoint and encrypts
  the message with the existing envelope format.
- The bot receives `encrypted_payload` and decrypts the envelope addressed to
  its public key in BotSDK.

## Bot to user

- BotSDK fetches the user's active device public keys through a new
  `GET /api/bot-api/users/{userId}/device-keys` endpoint.
- It encrypts one envelope per device and sends `sendMessage` with
  `encrypted_payload`.
- The server stores the ciphertext and fans out the normal encrypted message.

## Buttons and callbacks

- In `e2ee` mode the inline keyboard is part of the encrypted content.
- The server stores no `reply_markup`; the client renders buttons after
  decryption.
- `callback_data` is encrypted to the bot (`fcbenc:` + sealed box); the server
  forwards it as an opaque blob and the SDK decrypts it.
- `answerCallbackQuery` text is encrypted to the user's devices and decrypted
  in the client toast.

## Server constraints

- No Markdown validation, search indexing, moderation or push preview for
  e2ee bot messages.
- `messages.reply_markup` stays NULL in e2ee mode.
- Federation of e2ee bot chats is out of scope for the first version.

## BotSDK

BotSDK owns all crypto:

- key generation and storage;
- envelope opening;
- device-key fetch and cache;
- envelope creation for replies;
- encrypted button/callback payloads;
- opt-in `mode: "e2ee"`; plaintext mode remains the default for simple bots.

The root bot never uses BotSDK and remains `server` mode.

## Rollout

1. Add bot public-key registration and validation behind an internal flag.
2. Add device-key endpoint for bot tokens.
3. Add crypto support to the TypeScript SDK with shared test vectors.
4. Add encrypted text only; disable buttons in e2ee mode.
5. Add encrypted buttons and callback answers.
6. Only then allow `PUT /api/bot-api/encryption-key` to switch the mode.

## Remaining work

- A full browser E2E test of the encrypted client -> SDK -> client round trip.
- Bots in group chats are out of scope for the 1-1 bot protocol.
- Bot rotation has no key history: rotate in idle time, otherwise messages
  encrypted to the previous key until `key_version` propagates are lost.

Реализовано дополнительно: E2EE-вложения и локации (ключи/метаданные едут в
зашифрованном content), федеративные E2EE-чаты, identity-подпись v3 и
клиентский `id` для зашифрованной отправки.
