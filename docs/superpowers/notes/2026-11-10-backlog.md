## Приоритет 0: одновременный вход с разных устройств

Сейчас у аккаунта один токен: вход на втором устройстве перезаписывает
его, и первое устройство получает `401`. Нужны независимые сессии.

Спека: [2026-11-10-multi-device-design.md](../specs/2026-11-10-multi-device-design.md).

### Этап A — сессии

- Таблица `sessions`: `id`, `user_id`, `token_hash`, `created_at`,
  `expires_at`, `last_seen_at`, `user_agent`, `revoked_at`.
- `verify-code`, `refresh-token`, `complete-registration` создают/обновляют
  сессию, а не поле `users.token`.
- `logout` отзывает текущую сессию; отдельно — «выйти на всех устройствах».
- `AuthMiddleware`, SSE-auth и федеративные проверки смотрят на сессию.
- UI: список устройств и отзыв сессии.
- Учесть несколько SSE-соединений на пользователя, presence, push и звонки:
  входящий звонок звонит на все устройства, `accept` на одном закрывает
  звонок на остальных.

### Этап B — E2EE при нескольких устройствах

Решение по спеке: **Phase A — один ключ аккаунта + обязательное
восстановление из бэкапа; Phase B — ключ на устройство, отдельная спека.**
Новое устройство не генерирует ключ молча.

- Таблица `user_devices`: `id`, `user_id`, `public_key`, `created_at`,
  `revoked_at`, `last_seen_at`.
- Сообщение по-прежнему шифруется случайным ключом сообщения, но этот ключ
  запечатывается отдельно каждому активному устройству каждого участника
  чата. `keyId` в конверте становится идентификатором устройства.
- Своё устройство тоже получает конверт — иначе оно не прочитает
  отправленное с другого устройства.
- Старые сообщения (конверт с `keyId = userId`) остаются читаемыми как
  legacy-формат.
- Бэкап и отзыв ключей — по устройству.
- Плюс: нормальная изоляция и отзыв устройств.
- Минус: больше работы: миграция, список ключей, UI, тесты.

Рекомендация: этап A делать сразу, этап B — следующим крупным блоком.
До этапа B новое устройство без бэкапа не должно молча генерировать новый
ключ: нужен явный выбор «восстановить» или «начать с нового ключа» с
предупреждением, что старые сообщения останутся нечитаемыми.

## Приоритет 1: версия федеративного протокола

Сейчас соседи несут только подпись, timestamp и nonce; поля версии нет.
Любое несовместимое изменение ломает федерацию на время rolling-апгрейда.

- В `/.well-known/fast-chat` добавить `protocolVersions` (например, `[1, 2]`).
- В федеративные запросы добавить `X-Federation-Protocol`.
- Выбирать максимальную общую версию; при отсутствии общей — понятная
  ошибка, а не невнятный `401`.
- Поддержать текущую версию как `v1`, новую как `v2`; тесты на смешанные
  версии и поэтапный апгрейд.

## Федерация: группы и вложения

### Группы

Решение: **убираем искусственные ограничения и не делим группы на
«локальные» и «федеративные»**.

- Группа с одним создателем — валидное состояние. Сейчас это уже работает:
  `Store.CreateGroupChat` добавляет `ownerID` и разрешает пустой
  `memberIDs`. Убираем только верхний лимит.
- Убираем `maxGroupMembers = 100` как бизнес-ограничение. Если понадобится
  защита от злоупотреблений, это будет отдельная квота, а не «100 по
  умолчанию».
- Убираем запрет удалённых участников: `CreateGroupChat` и `AddChatMember`
  больше не должны требовать «все на одном сервере».
- Можно создать локальную группу, а потом добавить участника с другого
  сервера; для пользователя разницы нет.
- Для группы больше не работает модель «один `RemoteServer` на чат».

Модель: **сервер создателя — владелец группы**.

- Владелец хранит состав, имя, аватар и права; он же авторитет для
  добавления/удаления участников.
- Каждый сервер, у которого есть участники группы, держит реплику чата:
  тот же `chatId`, полный список участников, метаданные.
- Список серверов-участников выводится из ID участников (домен после
  двоеточия), а не хранится одним полем.
- Изменения состава и метаданных идут от владельца ко всем репликам.
- Сообщения отправляются на каждый сервер, где есть участники группы;
  текущую отправку «в один `chat.RemoteServer`» нужно заменить циклом.
- Для отображения удалённых участников нужен кэш профилей (ник, аватар)
  или федеративный запрос, потому что их нет в локальной таблице
  пользователей.
- Частный федеративный чат 1:1 остаётся как есть; это отдельный тип.

Технические детали, которые надо решить в спеке:

- сообщения идут напрямую с сервера отправителя на серверы участников или
  через сервер-владелец (рекомендация — напрямую, владелец только для
  состава и метаданных);
- как реплицируется удаление/выход участника и что видит удалённый
  участник;
- как работает catch-up, если сервер участника был офлайн;
- как проверять отправителя: подпись сервера + принадлежность `fromId`
  этому серверу + членство в реплике.

### Вложения

Решение: **начинаем с прокси через сервер получателя, файл не копируем.**

- Файл остаётся у загрузившего; нет дублирования и рассинхронизации.
- Клиент B просит свой `/api/files/{id}`; сервер B видит, что файл удалённый,
  и по подписанному федеративному запросу забирает его у сервера-источника,
  проверив доступ к чату.
- Для E2EE ключ файла уже лежит в зашифрованном сообщении, так что серверу
  достаточно отдать шифротекст.
- Минус — трафик идёт через сервер получателя. Позже можно добавить
  короткоживущую подписанную ссылку на сервер-источник, но не начинаем с неё:
  там нужны CORS/CSP и защита от хотлинка.

## Звонки: обновление страницы

Решение: **оставляем текущее поведение** — reload завершает звонок. Это не
приоритетная фича; перезвонить не проблема.

Главное требование: второй участник тоже должен получить завершение, а не
ждать таймаута. Сейчас это уже так: на reload/pagehide вызывается
`hangupCallOnLeave`, сервер завершает звонок и рассылает `call_ended`;
если запрос не дошёл, вторая сторона завершает звонок по обрыву соединения.
Проверить это тестом и не ломать при будущих изменениях.

Отдельный follow-up: caller сейчас не применяет ICE-серверы callee после
`accept` (union только у callee). Исправить через `setConfiguration` +
`restartIce` или повторный offer с полным union.

## STUN / TURN / coturn

Уточнение: coturn — это реализация TURN, а не STUN. Coturn умеет и STUN, и
TURN, но прежде всего это TURN-сервер.

Текущее состояние:

- STUN в конфиге уже есть: `config/dev.yaml` и `config/prod.yaml.example`
  используют публичный `stun:stun.l.google.com:19302`. Это не свой STUN, но
  он есть.
- TURN в dev выключен (`ice.turn: []`); в production-примере есть
  placeholder с `secret` и TURN REST API. Отдельного coturn-контейнера в
  репозитории нет.
- Приложение уже умеет выдавать короткоживущие TURN-креды через `/api/ice`.

Решение: **coturn в Docker для production; dev может использовать
публичный STUN/TURN. Выбор задаётся конфигом.**

- В dev — публичный Google STUN; TURN можно не поднимать или взять
  публичный Metered для проверки.
- В production по умолчанию — локальный coturn в Docker (STUN + TURN).
- Оба варианта уже выражаются текущим конфигом: `ice.stun` — список URL,
  `ice.turn` — список серверов. Ничего не хардкодим; можно указать
  публичный STUN/TURN или локальный coturn.
- Для production-примера добавить два варианта в комментариях: «локальный
  coturn» и «внешний/публичный STUN+TURN».
- Coturn-контейнер — отдельный compose; его можно включать профилем, чтобы
  в dev он не поднимался.

План Docker-обвязки (когда дойдём до звонков):

- официальный образ `coturn/coturn`;
- `turnserver.conf` с `use-auth-secret`, `static-auth-secret` из env,
  `realm`, `external-ip`, без анонимного доступа;
- порты: `3478/udp`, `3478/tcp`, при TLS — `5349/tcp`, плюс диапазон
  relay-портов UDP (например, `49152-65535`);
- для TURN желателен `network_mode: host` или аккуратный проброс портов;
- URLs для приложения: `turn:turn.example.com:3478?transport=udp`,
  `turn:...:3478?transport=tcp`; STUN — `stun:turn.example.com:3478`;
- секрет приложения (`FASTCHAT_TURN_SECRET`/`_FILE`) совпадает с
  `static-auth-secret` coturn.

Итог по окружениям:

1. **Dev:** Google STUN, TURN не обязателен. Для проверки TURN — Metered
   Open Relay или локальный coturn.
2. **Prod:** локальный coturn в Docker (STUN + TURN) по умолчанию.
   Альтернатива — внешний/публичный STUN+TURN, если прописан в конфиге.
3. **Managed TURN**, если не хочется администрировать: Metered Open Relay
   (бесплатный TURN, 20 GB/мес) для теста/MVP; Twilio Network Traversal
   Service или Cloudflare Realtime TURN для production. Проверить цены и
   лимиты.
4. Coturn запускать с `use-auth-secret` и тем же `static-auth-secret`,
   который задан в `FASTCHAT_TURN_SECRET` (или `_FILE`); статические
   логин/пароль не использовать.

Ссылки для выбора:

- coturn (self-hosted): https://github.com/coturn/coturn
- Metered Open Relay (бесплатный TURN/STUN, 20 GB/мес):
  https://www.metered.ca/tools/openrelay/
- Twilio Network Traversal Service:
  https://www.twilio.com/docs/stun-turn/faq
- Cloudflare Realtime TURN:
  https://developers.cloudflare.com/realtime/turn/

## Функции мессенджера

Порядок: сначала локальные версии, потом федерация для каждой сущности.

1. **Аватары пользователей.** Поле у пользователя, переиспользование файлов,
   правило доступа к файлу-аватару (как у аватара группы), отдача в
   `PublicUser`. Федерация: передача файла или прокси.
2. **Реакции.** Таблица `message_reactions`, агрегаты в DTO, SSE, sync,
   федеративный endpoint. Сервер увидит автора и эмодзи — это метаданные,
   не текст сообщения.
3. **Голосовые сообщения.** `MediaRecorder`, шифрованный upload,
   длительность/волна, лимит размера. Транскрипция — отдельная фича позже,
   после голосовых.
4. **Закрепление сообщений.** Таблица закреплений на чат, права
   (owner/admin в группах), список, SSE/sync.
5. **Блокировки.** Запрет сообщений, звонков, создания чата и поиска;
   в федерации удалённый сервер тоже должен уважать блокировку.
6. **Пересылка.** Клиент расшифровывает и заново шифрует в целевой чат;
   вложения нельзя переприкрепить без изменения правил владения файлом —
   нужна семантика forward/copy.
7. **Поиск по сообщениям.** При E2EE сервер не видит текст. Варианты:
   клиентский поиск по загруженным/расшифрованным сообщениям, локальный
   индекс (риск для приватности) или searchable encryption. Требует
   отдельного решения.

## Файловый кэш

Сейчас кэшируются просмотренные фото, аудио, зашифрованное видео и аватары:
до 200 записей, без лимита по байтам, вытеснение по времени добавления.

- Лимит на файл (не кэшировать крупные автоматически).
- Общий лимит кэша и проверка `navigator.storage.estimate()`.
- LRU по последнему доступу.
- «Сохранить офлайн» для крупных файлов.
- Не кэшировать видео/аудио автоматически без явного действия.

## Открытые вопросы

- Мультидевайс: этап A (сессии) делаем сразу; для этапа B выбрать общий
  ключ аккаунта или ключ на устройство. Рекомендация — ключ на устройство,
  но можно начать с общего и мигрировать.
- Если ключ на устройство — как восстанавливать новый девайс и отзывать
  старый?
- Вложения в федерации: решено начинать с прокси через сервер получателя;
  подписанная ссылка — возможное улучшение позже.
- Федеративные группы: решение — без различия локальных/федеративных,
  владелец — сервер создателя, лимит 100 убираем. Осталось решить в спеке:
  прямая рассылка сообщений по серверам участников или через владельца;
  как кэшировать профили удалённых участников; как реплицировать
  удаление/выход и catch-up.
- Поиск при E2EE: клиентский индекс или searchable encryption?
- Блокировки в федерации: локальный фильтр или федеративный список?
- Coturn: решено поднимать в Docker; осталось выбрать хостинг/VPS и
  TLS-сертификаты для `turns`.
